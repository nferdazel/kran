# T-133 — Sisa audit batch D: kontrak & API, DB, arsitektur, uji, UX, operasi

Status: **selesai** 25 Okt 2026. Sumber: audit 24 Okt 2026 — batch D (API-3/4/5/7/8, DB-6…DB-12,
ARC-3…ARC-12, LED-3…LED-7, UI-7…UI-13, OPS-11…OPS-16) plus MINOR/NIT sekitarnya (API-9/10/11,
DB-9/11, SEC-5/6).

Batch ini campuran: sebagian temuan nyata yang menutup lubang perilaku, sebagian perbaikan mutu uji,
dan sebagian keputusan arsitektur yang **tidak** dikerjakan sekarang. Aturan yang dipakai: setiap ID
yang tidak dikerjakan harus muncul di §"Batas yang dicatat" dengan dampak, cara mendeteksi, dan
pemilik — batas tanpa tiga itu bukan keputusan, hanya pekerjaan yang terlupa.

## 1. Yang diperbaiki

### Kontrak & API

| ID | Yang berubah |
|---|---|
| **API-3** | Kontrak kini mendeklarasikan `405` di **semua** 64 operasi, `501` + `503` di 61 operasi ber-`security`, dan `415` di 26 operasi ber-`requestBody` — semuanya respons yang benar-benar bisa datang dari router/penangan terakhir. `tools/openapi` menegakkannya (`Operation.secured`, `hasRequestBody`, `declaredStatuses`) sehingga operasi baru tidak bisa lupa; klien TS di-regenerate. |
| **API-4** | Badan non-JSON ditolak `415` di pembungkus (`acceptsJsonBody` + `pkUnsupportedMediaType`), sebelum router/handler menyentuh transaksi. Badan kosong tetap boleh. Kunci i18n `error_unsupported_media_type` (id+en) + pemetaan di `lib/app/errors.ts` (D-145). |
| **API-5** | `Idempotency-Key` yang ada tetapi tidak sah (kosong setelah trim, > 200 karakter, karakter kontrol) → `400` di `POST /deposit/accounts`, bukan `500` dari `ValueError` di dalam transaksi. |
| **API-10** | `X-Request-Id` dari klien disaring (`sanitizeCorrelationId`): hanya `[A-Za-z0-9._:-]`, maksimum 64 karakter; nilai lain diganti id baru (bukan dipotong, supaya tidak bertabrakan). |
| **API-11** | Batas `minimum`/`maximum` schema parameter kini berlaku untuk nilai **string desimal** (`isDecimalString`), jadi `limit_withdrawal="-1.00"` ditolak saat submit/approve. Tanggal/enum/teks tidak tersentuh (D-146). |

### Basis data

| ID | Yang berubah |
|---|---|
| **DB-9** | `modules/ledger/migrations/0047_ledger_line_gl_index.sql`: index `journal_line(gl_account)` — kolom FK + `GROUP BY` laporan tanpa index. |
| **DB-11** | `modules/platform/migrations/0048_platform_audit_action_index.sql`: index `audit_log(action text_pattern_ops)` untuk filter `LIKE 'x%'`. |
| **DB-8** | `modules/platform/migrations/0049_platform_audit_prev_hash_unique.sql`: `UNIQUE (prev_hash)` — percabangan rantai audit kini ditolak basis data, bukan hanya terlihat saat verifikasi manual. Kedua DB yang ada diperiksa lebih dulu (0 percabangan). Index ini **membongkar bug laten**: `platform.audit_log_chain` memilih ujung rantai dengan `ORDER BY seq DESC`, padahal `seq` dialokasikan sebelum advisory lock sehingga dua penulisan bersamaan bisa commit terbalik — append berikutnya lalu merantai ke baris yang bukan ujung (cabang). Tanpa index, cabang itu senyap; dengan index, setiap operasi teraudit akan gagal 500. `modules/platform/migrations/0050_platform_audit_chain_tail.sql` mengganti fungsinya: ujung rantai = baris yang `hash`-nya tidak dipakai sebagai `prev_hash` baris lain (murah karena index 0049). |

## 3. Bukti

Semua perintah dijalankan di repo ini (macOS, dev DB dari `.local/dev.env`).

- `./task check` → hijau: format, `nim check` (229/230 berkas), `archcheck`, `lint-nomagic`,
  `paramgen --check` ("in sync"), i18n, dan **8 skrip** `bash -n` + `shellcheck`.
- `./task openapi` → kontrak lolos lint, klien TS sinkron, typecheck paket klien hijau (setelah
  `./task openapi-gen` untuk 405/501/503/415).
- `./task test topenapi` → termasuk tiga aturan baru: `405`, `501`, `503`, `415` + dua test positif.
- `./task test tcontract` → parity rute ↔ kontrak hijau dengan aturan baru.
- `./task test itapi_deposit` → `415` untuk `text/plain` dan untuk badan tanpa `Content-Type`, dengan
  `code = UNSUPPORTED_MEDIA_TYPE`, tanpa rekening/audit yang tercipta; `400` untuk kunci idempotensi
  tidak sah (3 bentuk).
- `./task test tparam` → batas string desimal (`"-1.00"` ditolak, `"1.5"` di atas maximum ditolak,
  tanggal/enum tidak tersentuh) + `isDecimalString` (5 bentuk sah, 9 bentuk ditolak).
- `./task test thttp_util` → `sanitizeCorrelationId` (nilai wajar dipakai, kosong/kepanjangan/
  karakter lain diganti).
- `./task test tlogin_guard`, `./task test itapi_users` → pembatas login tetap hijau dengan default.
- `./task dbtools validate` → 84 migrasi (4 baru: 0047, 0048, 0049, 0050); `./task dbtools migrate`
  → keempatnya diterapkan di dev DB.
- `./task test itplatform` → termasuk dua test baru: rantai bercabang tetap **terdeteksi**
  verifikasi (data lama/restore) dan percabangan **baru ditolak** basis data; plus kontrol bahwa
  append setelah dua transaksi bersisipan menempel ke ujung rantai yang benar (sebelum 0050, append
  itu ditolak index unik — bukti bug latennya nyata, bukan teoretis).
- `caddy validate --adapter caddyfile` (Caddy 2 di server, berkas sementara di `/tmp`, dihapus lagi)
  → `Valid configuration` untuk blok `request_body` + transport baru.
- Pemeriksaan langsung di produksi (baca saja): `platform.audit_log` 102 baris, **0** percabangan
  `prev_hash`, **0** baris genesis ganda — prasyarat index unik DB-8 terpenuhi. Env-file produksi
  `600 sachiel sachiel`, jadi pemeriksaan mode/owner OPS-16 tidak menghalangi deploy berikutnya.
- `./task ci` (penuh) dan `./task e2e`: lihat `docs/PROGRESS.md` entri 25 Okt 2026.

## 4. Catatan

- **Perubahan perilaku yang disengaja**: badan tanpa `Content-Type: application/json` sekarang 415.
  Ini memengaruhi skrip manual/`curl` yang lupa header; klien aplikasi (openapi-fetch) selalu
  mengirimnya.
- `ops/caddy/Caddyfile.kran.example` bukan berkas yang berjalan di server: Caddyfile live memakai
  `import` (snippet `base_security_headers`, `log_access`) dan CSP berbeda. Perubahan OPS-14 karena
  itu **belum** berlaku di produksi sampai blok yang sama ditambahkan ke `/etc/caddy/Caddyfile` dan
  `systemctl reload caddy` dijalankan manusia. Contoh di repo sudah menyimpang dari live sejak
  sebelumnya (CSP), dan itu tidak diubah di batch ini.
- `MemoryMax` di unit quadlet adalah pengaman kebocoran, bukan hasil pengukuran; angka dan alasannya
  ada di komentar unit.
- **Temuan tambahan (di luar daftar audit)**: ujung rantai audit dipilih lewat `seq`, bukan lewat
  rantai. Ditemukan karena index unik DB-8 membuat append setelah dua transaksi bersisipan gagal,
  dan ditutup di migrasi 0050 dengan test yang membuktikannya. Produksi saat ini 0 percabangan,
  jadi bug itu belum pernah termaterialisasi di sana.
- Audit ID yang sudah tertutup di batch lain tidak diulang di sini: API-1/6 dan ARC-1/2 (T-130),
  API-2/SEC-1…SEC-4 (T-128), DB-1…DB-5 dan LED-1/LED-2 (T-129), UI-1…UI-6/UI-11 (T-132),
  OPS-1…OPS-10 (T-131), DB-9/DB-11/ARC-11/ARC-12/SEC-5 (batch ini, lihat §1).
