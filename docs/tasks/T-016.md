# T-016 — Layanan parameter (lapisan application)

Spec: §10.3 (resolusi & cache), §10.4 (akses bertipe, startup check, drift), §5.1 (batas
lapisan: `application` bicara ke port, bukan driver DB).

## Scope

T-005 menyelesaikan penyimpanan & resolusi parameter di `infrastructure`; sisa lapisan
application dipisah ke task ini supaya tidak ada pekerjaan "setengah jadi" (AGENTS.md §5).

1. `application/param_cache.nim` — cache in-proc per (key, scope, tanggal), hit/miss counters,
   invalidasi per key / seluruhnya. Murni (tanpa DB).
2. `application/param_service.nim` — port `ParamSource` + `ParamService.get[T]` (akses bertipe),
   `snapshotOf`, `invalidate`. Application **tidak** menyentuh driver DB (archcheck rule B).
3. `application/param_drift.nim` — pembanding definisi kode (`kernel/generated/paramkeys`) vs DB
   (`platform.param_definition`): key yatim, tipe/module/scope/sensitivitas/approval berbeda.
4. `infrastructure/param_source_db.nim` — adaptor: `dbParamSource`, `dbDefinitions`,
   `driftAgainstDatabase`, `watchParamChanges` (NOTIFY → invalidasi cache).
5. Test: `tparamservice.nim` (13, murni) + `itparamservice.nim` (6, integrasi DB).

## Keputusan desain

- **Cache tanpa TTL, invalidasi eksplisit.** Nilai parameter berubah karena *keputusan*
  (maker-checker), bukan karena waktu; TTL akan membuat perilaku tak terduga ("kadang lama,
  kadang baru") tanpa manfaat. Karena nilai **efektif-dated**, tanggal buku ikut jadi bagian
  kunci cache (§10.3) — `get(key, asOf, scope)`.
- **Port, bukan import DB.** `ParamSource.fetch` adalah proc bertipe `Result[ParamSnapshot,
  ParamError]`; adaptor DB (dan fake di test) mengisinya. Archcheck membuktikan larangannya
  dengan probe nyata (lihat bukti di bawah).
- **Validasi tetap satu tempat.** `ParamSnapshot` (nilai + tipe + schema) tinggal di
  `domain/param.nim` dan konversi memakai `checkedSnapshot`, sehingga hit cache dan ambil-baru
  divalidasi dengan aturan yang identik.
- **Watcher dijalankan oleh pemanggil, bukan thread.** `watchParamChanges` menunggu NOTIFY
  dengan timeout dan meng-invalidasi cache; pemanggilnya adalah event loop aplikasi
  (T-009 SSE hub) yang memang sudah memegang koneksi `LISTEN`. Tidak ada thread/lock tambahan
  di Fase 0 — dicatat sebagai O-018 supaya tidak terlupa saat server HTTP lahir (ADR-002).
- **Drift guard** dijalankan di startup dan di test integrasi; memakai daftar definisi hasil
  paramgen (kode) vs isi tabel (DB), jadi tidak perlu query khusus di luar `platform`.

## Kriteria selesai (dari backlog)

| Kriteria | Bukti |
|---|---|
| `application/` tidak mengimpor driver DB (archcheck) | `./task archcheck` bersih; probe nyata: menambahkan `import db_connector/db_postgres` ke `application/probe_bad.nim` → terdeteksi `[B] application harus bicara ke port, bukan driver DB` (berkas probe dihapus setelah uji) |
| Cache invalid setelah NOTIFY | `itparamservice`: perubahan lewat `submitChange`/`approveChange` di koneksi pendengar → `watchParamChanges` mengembalikan key → nilai baru terbaca (sebelum invalidasi masih nilai lama) |
| `get` bertipe mengembalikan nilai aktif | `tparamservice` (integer/json, error tipe & schema) + `itparamservice` (nilai pack: `fiscal_year_start_month` = 1, `session_idle_minutes` = 30; scope cabang jatuh ke GLOBAL; efektif-dated: tanggal sebelum perubahan masih nilai lama) |
| Drift DB vs generated terdeteksi | `tparamservice` (semua jenis drift) + `itparamservice`: `driftAgainstDatabase(db, paramDefinitions)` == 0 temuan setelah seed |

## Batasan yang diketahui (jujur)

1. **Belum ada thread/watcher otomatis**: invalidasi harus "dipompa" oleh pemanggil
   (`watchParamChanges`). Keputusan: menunggu event loop T-009 (ADR-002). O-018.
2. **Cache belum dibatasi ukuran**: kunci memuat `asOf`, jadi tanggal buku yang terus maju
   menambah entri. Volume kecil (jumlah parameter × scope aktif), tetapi purge berbasis tanggal
   belum ada — dicatat di tugas lanjutan bila terbukti tumbuh.
3. **Belum ada metrik cache** (hit ratio) ke endpoint observabilitas; counters sudah tersedia
   di `ParamCache` untuk dipakai nanti.
4. **Alih O-012**: konvensi lookup scope masih membuat nilai level `INSTITUTION` (id konkret)
   tidak terbaca dari konteks cabang — belum diubah di task ini karena menyentuh semantik
   resolusi T-005 dan perlu keputusan pemilik.
