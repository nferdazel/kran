# T-009 — Realtime hub (outbox → klien WebSocket, resume token)

Spec: §19.1 (realtime lewat endpoint yang sama, amplop `id`/`topic`/`payload`), §19.2 (reconnect
tanpa kehilangan peristiwa), §12.4 (skema event di `packages/contracts/events`), §13 (kontrak =
sumber kebenaran), §18.2 (permukaan serangan), ADR-002/D-019 (Mummy + WebSocket).

## Scope

1. `modules/platform/migrations/0007_platform_outbox_notify.sql` — trigger `AFTER INSERT` pada
   `platform.outbox` yang `pg_notify('cbs_outbox', outbox_id)`.
2. `modules/platform/application/realtime.nim` — hub **murni**: topik, langganan, fanout, amplop
   pesan (`encodeEvent`/`encodeSubscribed`/`encodeResync`/`encodeError`), pembacaan pesan kontrol
   klien (`decodeSubscription`), penyaringan topik per izin (`splitAllowed`).
3. `modules/platform/infrastructure/outbox_listener.nim` + `outbox_repo.fetchAfter`/`latestEventId`
   — `LISTEN` kanal `cbs_outbox`, tunggu notifikasi, baca peristiwa setelah token.
4. `apps/api/src/events.nim` — transport: handshake WS (`openStream`), state koneksi, otorisasi
   topik (`TopicPolicy`), replay/resume, pump (thread `LISTEN` → hub → soket).
5. `apps/api/src/context.nim` — `AppContext` dipindah dari `health.nim` supaya modul fitur
   (`events`) bisa dipakai tanpa impor melingkar; `health` me-*re-export* `context`.
6. Kontrak: operasi `GET /api/v1/events/stream` (101/401/403/405/426/500/501) +
   `packages/contracts/events/realtime-envelope.v1.schema.json` (skema amplop, spec §12.4).
7. Test: `trealtime` (hub murni), `itrealtime` (outbox → NOTIFY → baca tabel → fanout),
   `itapi_ws` (klien WebSocket nyata: 426/401/403, pengiriman langsung, penolakan topik, pesan
   tidak valid, unsubscribe, resume, resync), tambahan 1 test di `tapi` (rute tanpa layanan → 501).

## Keputusan desain

- **NOTIFY di INSERT, bukan di dispatcher.** UI perlu tahu peristiwa begitu peristiwa itu durable;
  kalau disinyalkan dispatcher, layar diam saat dispatcher tertunda — dan role worker belum ada
  (O-013). Dispatcher tetap memegang status `PENDING→DONE/DEAD` (spec §12.4). Payload NOTIFY hanya
  `outbox_id`: sinyal "ada yang baru", bukan pengangkut data (tidak ada batas 8000 byte, satu
  sumber kebenaran).
- **Hub murni, transport terpisah.** `application/realtime.nim` tidak menyentuh soket/DB, jadi
  aturan topik & resume diuji tanpa I/O, dan mengganti transport kembali ke SSE tidak menyentuh
  logika (spec §12.2 satu arah dependensi).
- **Resume token = `outbox_id`.** Urutan replay memakai kolom `seq` (`bigint identity`), bukan
  urutan `occurred_at` yang bisa sama; token tak dikenal/di-purge diperlakukan sebagai "mulai dari
  awal" (klien de-dup by `id`) — lebih baik daripada kehilangan peristiwa diam-diam (§19.2).
- **Tanpa antrean per-langganan.** Rencana kirim dibuat di hub, eksekusi di transport (Mummy yang
  mengantre keluar). Kuota per klien lambat belum ada → O-028; mekanisme "buffer penuh → resync"
  sengaja **tidak** dibuat karena tidak ada sinyal "sudah terkirim" dari transport, dan abstraksi
  tanpa sinyal hanya jadi gate palsu.
- **Default menolak (`denyPolicy`).** Identitas diambil dari cookie `cbs_session` (spec §13) atau
  `Authorization: Bearer`, tetapi sampai sesi nyata terpasang (T-012) kebijakan default menolak
  semua koneksi (403). Endpoint tertutup lebih baik daripada terbuka; uji menyuntikkan kebijakannya
  sendiri. Topik yang ditolak **dilaporkan** (`subscribed.denied`), bukan dibuang diam-diam.
- **Batas replay**: `resumeLimit` per putaran dan `maxResumeBatches` putaran; kalau peristiwa yang
  terlewat melebihi itu, klien menerima `resync` dan harus menyegarkan keadaan lewat HTTP. Batas
  ini konfigurasi transport (`apps/api`), bukan literal di lapisan application.
- **Pump "mulai dari sekarang".**`lastEventId` di-seed ke peristiwa terakhir saat pump menyala;
  backlog lama tidak disemprotkan ke klien baru (riwayat diambil lewat `resumeFrom`/HTTP). Sinyal
  kesiapan `pumpReady()` disediakan supaya uji tidak menebak lewat `sleep`.

## Kriteria selesai (dari backlog)

| Kriteria | Bukti |
|---|---|
| Peristiwa dari outbox sampai ke klien | `itrealtime` (INSERT → trigger NOTIFY → pendengar → baca tabel → fanout) + `itapi_ws` "peristiwa outbox dikirim ke klien yang berlangganan topiknya" (klien WS nyata menerima frame `{"type":"event",…}` dengan `id`/`topic`/`payload` yang sama, divalidasi terhadap skema amplop kontrak) |
| Reconnect tanpa kehilangan peristiwa (resume) | `itapi_ws` "reconnect dengan resumeFrom menerima peristiwa yang terlewat, berurutan" (`resumed=2`, urut, token tidak diulang) + "resume dengan token tak dikenal → replay dari awal" + "kehilangan melebihi batas replay → resync" |

## Bug nyata yang tertangkap

1. **Topik langganan tidak sampai ke hub.** `handleSubscription` menyimpan topik di state koneksi
   tetapi tidak memperbarui langganan di hub → peristiwa tidak pernah dikirim. Tertangkap oleh
   `itapi_ws` (dan hanya oleh test ujung-ke-ujung itu; `trealtime` unit tetap hijau karena hub-nya
   benar). Perbaikan + pengecekan ulang topik tepat sebelum menulis soket (menutup balapan
   `unsubscribe`).
2. **Validator kontrak bisa mati (bukan gagal).** `tools/openapi/lib.nim` memakai
   `schema{"additionalProperties"}.kind`; operator `{}` mengembalikan `nil` bila kunci tidak ada →
   dereference nil → SIGSEGV saat memvalidasi skema amplop (properti bebas bentuk seperti
   `payload`). Diperbaiki dengan pemeriksaan `nil`; kelas bug ini justru yang dilarang header
   `lib.nim` ("validator yang diam = gate palsu").
3. **Klien uji "tidak pernah menerima" respons kecil.** `recv(socket, data, size, timeout)` di Nim
   menunggu **seluruh** `size` byte; membaca header HTTP sebesar 4096 byte lalu kalah sabar =
   `TimeoutError` yang membuang data yang sudah dibaca. Perbaikan: baca header satu byte per
   panggilan (`readByte`), lalu panjang pasti untuk frame. Konsekuensi: klien WS minimal ~170 baris
   ada di `apps/api/tests/wsclient.nim` (bukti soket nyata, tanpa dependensi baru).

## Batasan yang diketahui (jujur)

1. **Query kuota/topik dari klien belum dibatasi rate** — belum ada rate limit per koneksi (spec
   §18.2); batas yang ada hanya jumlah/panjang topik per pesan langganan.
2. **Pump mati tidak terlihat operator**: `pumpReady()` disediakan, tetapi `/readyz` belum
   memeriksanya, dan tidak ada log saat pump berhenti → O-029.
3. **Batch replay memakai `resumeLimit` global**, bukan per-klien; klien yang tertinggal sangat jauh
   menerima `resync` dan harus menyegarkan lewat HTTP (belum ada endpoint "ambil sejak id" khusus
   UI; T-012 memakai audit/param list + resume).
4. **Tidak ada heartbeat/ping server-side**; koneksi mati (NAT/proxy) baru diketahui saat kirim
   berikutnya. Mummy menjawab ping klien, jadi klien bisa menjaga koneksi.
5. **`subscriptionLimits` (32 topik, 128 karakter) ada di transport** (`apps/api/src/events.nim`),
   bukan parameter DB — nilainya pertahanan protokol, bukan nilai bisnis (spec §10.4); keputusan
   dicatat D-021 dan tetap terbuka bila nanti perlu dijadikan parameter (O-030).
6. **`allowAllPolicy()` hanya untuk uji** — ia hidup di `events.nim` (dipakai test transport), bukan
   konfigurasi default; produksi memakai `denyPolicy()` sampai T-012 memasang otorisasi sesi.
