## Scope

### Why purge is not an option

Four independent reasons, each of which alone would be enough:

1. **The schema refuses it, by design.** `audit_log_no_change_trg` raises on `UPDATE`/`DELETE` per row
   and `audit_log_no_purge_trg` on `TRUNCATE` (`0002_platform_audit_log.sql`); `0042` revokes
   `UPDATE, DELETE, TRUNCATE` on `platform.audit_log` from `kran_runtime` (D-110, O-010). A purge
   task therefore means dropping a guard, and AGENTS §1.9 forbids weakening a gate without a new
   approved decision.
2. **A prefix delete breaks verification on the row that survives it.** `link_ok` in `0011` is
   `prev_hash = genesis OR EXISTS(row with that hash)` and `NOT EXISTS(other row with the same
   prev_hash)`. Delete the first row and the new first row points at a hash that no longer exists:
   `link_ok` goes false and `ctl verify-audit` exits 1 on data that is not damaged, so every later
   manual verification reports a break and the anchor comparison can no longer separate a real break
   from an expected cut. D-206 records exactly this.
3. **It shortens evidence, which the floor forbids.** D-206 keeps audit for at least ten years
   (UU 8/1997, UU KUP Pasal 28 ayat (11)). Rotation does not shorten it: the rows move to an archive
   that stays under the same floor. A purge deletes them.
4. **A correct delete and a malicious one look identical afterwards.** Without an external witness,
   removing a middle segment produces a shorter chain that verifies. L-13 already says the anchor is
   the only thing that catches a rewrite; the same is true of a cut.

### The chain baseline, recorded before any row is removed

New table `platform.audit_chain_baseline`, one row per rotation, append-only by trigger, no grants
for `kran_runtime`:

| Column | Meaning |
|---|---|
| `baseline_id` | uuid, primary key |
| `created_at` | timestamptz, default `now()` |
| `cut_seq` | `seq` of the last archived row **in chain order** |
| `cut_hash` | `hash` of that row; this is the `prev_hash` the first surviving row already carries |
| `planned_rows` | rows the rotation intends to remove |
| `first_kept_seq` | smallest surviving `seq` at plan time, `NULL` when the rotation empties the table |
| `archive_path` | absolute path of the exported file, outside the database |
| `archive_sha256` | digest of that file, computed before any delete |
| `actor`, `reason` | who ran it and why now (disk headroom, incident); both required, non-empty |

`UNIQUE (cut_hash)`: two rotations cannot claim the same boundary.

`platform.audit_verify()` gains exactly one clause:

```
link_ok = (a.prev_hash = repeat('0', 64)
           OR EXISTS (SELECT 1 FROM platform.audit_log b WHERE b.hash = a.prev_hash)
           OR EXISTS (SELECT 1 FROM platform.audit_chain_baseline s WHERE s.cut_hash = a.prev_hash))
          AND NOT EXISTS (SELECT 1 FROM platform.audit_log c
                          WHERE c.prev_hash = a.prev_hash AND c.seq <> a.seq)
```

Nothing else in the predicate moves: `row_hash_ok` is unchanged, the fork check is unchanged, and a
row whose `prev_hash` is neither a live hash, the genesis sentinel, nor a recorded `cut_hash` still
reports `link_ok = false`. That is what keeps the check honest rather than relaxed.

The baseline is written **before** the first delete, in its own committed transaction, together with
the archive file and its digest. A crash after that point leaves a state that still verifies: the
first survivor's `prev_hash` equals `cut_hash`, which the baseline already covers. A re-run finds the
open boundary and continues. Deletes then run in batches, each its own transaction, so the advisory
lock on the chain is not held for the whole rotation.

The rotation appends one audit row, action `platform.audit.archive`, carrying `cut_seq`, `cut_hash`,
`planned_rows` and `archive_sha256`, in the transaction that removes the last batch. After that the
new chain starts with a row that records its own origin.

### Bounds: chain prefix, not partition

- **Declarative partitioning is rejected.** A unique index on a partitioned table must include the
  partition key, so `audit_log_prev_hash_unique_idx` (0049) would have to become
  `(prev_hash, <partition key>)`; the same `prev_hash` could then appear once per partition, which is
  exactly the fork 0049 exists to make impossible. Partitioning the audit log would trade a real guard
  for a storage convenience.
- **The bound is a chain prefix, computed by walking `prev_hash` from the genesis row.** `seq` order
  is not chain order: `seq` is allocated before the chain trigger takes its advisory lock, so a
  higher `seq` can commit first (O-038, reproduced deterministically in `itplatform.nim:271`).
  `DELETE ... WHERE seq <= N` would therefore cut a hole in the middle of the chain instead of a
  prefix, and could remove the genesis while keeping its successor. The command walks
  `hash = prev_hash` links from `repeat('0', 64)` for the requested number of rows and takes the last
  row reached as `cut_seq`/`cut_hash`.
- **Per-run bound.** `--rows=<n>` (required) is how many chain rows this run may archive, and
  `--chunk=<n>` (required) is the delete batch size. No default in code: a hidden constant here would
  be a policy decision nobody signed. No period is involved — L-44's trigger is disk headroom, and the
  operator states the bound and the reason in the same command.
- **Archive target.** `--out=<dir>` writes `<dir>/audit-<cut_seq>-<cut_hash>.copy` (fixed column
  order, chain order) plus `<file>.json` with `cut_seq`, `cut_hash`, row count, `archive_sha256` and
  the anchor line printed at plan time. The directory is a host path outside the database and outside
  database dumps, like the anchor file. The task never deletes an archive file and never compresses
  or prunes the directory; copying it off-host stays an operator step (L-03, L-04, T-249).

### Privilege

The delete runs as the owner role, through the existing privileged entry point
`kran-api --role=migrate --archive-audit`, with the same `MIGRATE_DB_URL_HOST` DSN the deploy uses for
migrations (`ops/scripts/deploy-vps.sh:416-422`). `kran_runtime` cannot `DELETE` by design and the
command must not pretend otherwise: it probes
`has_table_privilege('platform.audit_log','DELETE')` first and exits **2** with a clear message when
it lacks the privilege, before writing a baseline row or an archive file.

Not a daycloser task: it deletes evidence, needs the owner DSN, and needs a written reason per run.
The outbox/inbox purge in T-282 is different — it deletes history past a signed window, unattended.

- Any retention period for audit, and any change to D-206's numbers or to `platform.audit_log`'s
  floor.
- The off-host copy of the anchor and of the archive directory (T-249, owner action).

## Acceptance

1. **Rotated chain verifies.** `itarchive` seeds a 40-row chain, archives the first 25 and asserts
   `SELECT count(*) FROM platform.audit_verify() = 15` with every `row_hash_ok` and `link_ok` true.
   *Fails on the parent commit*: deleting the same 25 rows with the guard disabled and no baseline
   leaves the first survivor at `link_ok = false` — that assertion is the one this task turns green.
2. **The check is extended, not weakened.** Deleting a prefix without inserting a baseline row still
   yields `link_ok = false` on the first survivor, and a row whose `prev_hash` is a random 64-hex
   string still yields `link_ok = false`. Both cases pass on the parent too, which is the point: they
   must not regress.
3. **The bound is a chain prefix.** Reusing the deterministic out-of-order shape from
   `itplatform.nim:271`, a row with the larger `seq` but the earlier chain position is archived, and a
   row with the smaller `seq` but the later chain position survives. Asserted by `seq`, not by count.
4. **Guards intact.** As `kran_runtime`: `DELETE` and `TRUNCATE` on `platform.audit_log` still raise
   `restrict_violation`, and `UPDATE`/`DELETE` on `platform.audit_chain_baseline` are denied by grant.
   As the owner: `UPDATE`/`DELETE` on the baseline table raise from its own append-only trigger, and
   `TRUNCATE` raises too. `itplatform` `:198` stays green unmodified.
5. **Refusal is fail-closed.** Running the command with a DSN that cannot delete exits 2, writes no
   baseline row, and creates no file.
6. **Resumable and idempotent.** Interrupting after the baseline commit and before the first delete,
   then re-running, completes to the same 15 rows with `link_ok` true. A second run with the same
   `--rows` exits 0 and reports 0 rows deleted.
7. **Archive fidelity.** Re-importing the archive file into a scratch schema and verifying
   archive+suffix as one chain reports zero broken links, and the file's sha256 equals the value in
   the manifest and in the baseline row.
8. **Anchor seam.** The rotation prints an anchor line carrying `cut_seq`, `cut_hash` and
   `archive_sha256`; `ctl verify-audit` exits 0 after the rotation; the audit row with action
   `platform.audit.archive` exists exactly once per rotation.
9. **Gates.** `./task check-fast` green (includes `lint-nomagic`, `paramgen --check`, i18n),
   `./task test archive` green, `./task test platform` green, `python3 tools/docsgen/docsgen.py --check`
   green after `SCHEMA.md` is regenerated.

## Rollback

- **Code**: revert the commits. The migration is expand-only; `--down` of `0106` is safe **only while
  no rotation has run**, because dropping the baseline table returns `audit_verify()` to the `0011`
  predicate and any already-rotated chain would then report `link_ok = false` on its first row.
- **Data, after a rotation**: re-import the archived rows from the archive file in one transaction,
  verify that the file's sha256 matches the baseline row, delete the baseline row last, and only then
  revert the function. The order matters: the baseline row must outlive the re-import.
- **Data, after a rotation that emptied the table**: the same re-import, with the new chain's rows
  left in place; the re-imported prefix chains onto `prev_hash = repeat('0',64)` only if the live
  chain was emptied, so the procedure states the two cases separately.
- Nothing is unrecoverable as long as the archive file exists: the delete is the only step that
  removes rows, and it runs after the file and its digest are committed.

  rotation copies a chain-order prefix to a file outside the database, records
  `platform.audit_chain_baseline` (`cut_seq`, `cut_hash`, `archive_sha256`, actor, reason) before the
  first delete, and `audit_verify()` accepts a `prev_hash` that matches a recorded `cut_hash`.

  immutable triggers is a guard weakening; growth still has to be bounded. Consequence: amends the
  L-44 sentence "needs its own decision"; adds a baseline table that is itself a guard and therefore
  needs the same append-only treatment as the audit log.
- **Residual risk, written down rather than hidden**: a role that can write the audit table can also
  insert a baseline row with a forged `cut_hash`, legitimising a fabricated seam. The mitigation is

  L-13, not in a claim that the baseline makes the chain stronger than the anchor already does.
