# T-113 — Test konkurensi top-up vault deterministik

Status: **test ditulis** (belum dijalankan di DB/CI — gate pemilik). Tidak ada perubahan kode
produksi. Item review T-107.

## Scope

- Ganti test konkurensi top-up vault yang bergantung timing (dua request HTTP tanpa penahanan bisa
  berurutan, sehingga tidak membuktikan apa pun) dengan test **deterministik** berpola `ittransfer`:
  koneksi penahan lock + tunggu transitif `pg_blocking_pids`.
- Tidak masuk: mengubah handler/repo. Kode sudah memakai `balance = balance + ?` (increment atomik,
  `creditVault`), jadi tidak ada bug yang dilaporkan.

## Desain sinkronisasi

Berkas: `apps/api/tests/itapi_teller_vault.nim`, suite *"vault: dua top-up bersamaan deterministik
(T-113)"* (menggantikan suite lama).

1. Patok saldo vault `BranchRace` = `100.0000` (tidak bergantung urutan suite lain).
2. **Koneksi penahan** (`dbPool.acquire()`): `BEGIN`, `SELECT 1 FROM teller.vault WHERE branch_id =
   ? FOR UPDATE`, catat `pg_backend_pid()` sebagai `holderPid`. Selama dipegang, `creditVault`
   (`UPDATE teller.vault SET balance = balance + ?` — kunci baris implisit) pada pekerja mana pun
   **wajib menunggu** di baris ini.
3. Dua worker HTTP in-process (`topUpWorker`, thread + HTTP client, pola test yang ada) dengan
   `Idempotency-Key` berbeda: 30.0000 dan 20.0000.
4. Tunggu **transitif** sampai `blocked == 2` lewat `blockedByHolder(holderPid)` — CTE recursive
   `pg_blocking_pids` (penunggu kedua bisa mengantre di belakang penunggu pertama, maka rantai
   ditelusuri rekursif). Batas 5 s; `sleep(20)` hanya polling, **bukan** penentu sinkronisasi.
5. `COMMIT` koneksi penahan (dilepas **tanpa syarat**, sebelum assertion, supaya pekerja tidak
   pernah menggantung), `joinThread`.
6. Assert `blocked == 2`, dua 201, saldo akhir `150.0000`.

Setelah kedua 201, replay `key1` (body sama) diassert `200` + `Idempotent-Replayed` dan saldo tetap
`150.0000` (replay tidak menambah saldo).

Tidak memakai `sleep` sebagai penentu urutan; `sleep` hanya jeda polling di antara query
`pg_blocking_pids`.

## Mutation check (dijelaskan, TIDAK dijalankan)

Ganti increment atomik `balance = balance + ?` menjadi read-then-write (mis. baca saldo lalu
`UPDATE ... SET balance = ?`). Kedua pekerja membaca `100` sebelum menunggu lock (SELECT tidak
diblokir oleh `FOR UPDATE` penahan), lalu menulis `130`/`120` → saldo akhir ≠ `150` dan assertion
`vaultOf(BranchRace) == "150.0000"` **GAGAL** (lost update). Karena lock ditahan sampai **kedua**
pekerja menunggu, jalur balapan itu benar-benar terekspos — berbeda dari test lama yang hanya
berharap dua request kebetulan bersamaan. Mutasi lain yang sama-sama harus mematikan test ini:
menghapus `Idempotency-Key` (replay jadi 400/201 ganda).

## Risiko flake

- Jika salah satu worker gagal **sebelum** menyentuh `creditVault` (mis. 401/403/404), ia tidak
  pernah menunggu → `blocked < 2` → test gagal. Setup (token `platform_admin` di cabang, vault ada)
  membuat ini tidak terjadi.
- Jika server HTTP menyerialkan request, `blocked` tak pernah 2 → gagal pada batas 5 s. Mummy
  memakai pool worker `countProcessors() * 10`, jadi tidak menyerialkan.
- Batas blok DB `KRAN_DB_QUERY_DEADLINE_MS` (default 20 s) harus > 5 s; lock dilepas jauh di bawah
  itu.
