# T-048 — O-057: samakan `missingActiveKeys` dengan aturan resolusi

Status: **DONE** (16 Okt 2026).
Prioritas: P1 (kebenaran: jalur startup vs jalur baca runtime).
Keputusan terkait: D-041 (lookup scope bertipe), D-046 butir 6 (tanpa fallback antar level).

## Kenapa

`missingActiveKeys` (startup check, spec §10.4) memakai aturan "aktif" yang **berbeda** dari
`resolveCandidate` (resolusi yang dipakai aplikasi saat membaca parameter). Selama dua definisi
"aktif" hidup berdampingan, startup check bisa menyatakan sehat sementara pembacaan runtime gagal
(`ParamNotFound`) — atau sebaliknya.

## Temuan (recon, jangan menebak)

### a. Bagaimana aplikasi **benar-benar** membaca key

Resolusi runtime = `resolveCandidate(candidatesOf(...), lookupFor(scope))`:

- `domain/param.nim:67` — `resolveCandidate`: `GLOBAL` **selalu** cocok; level lain cocok **hanya**
  bila `lookup(scopeType) == some(id)` dan `id == c.scopeId` (`wanted.isNone or wanted.get() !=
  c.scopeId` → dilewati).
- `domain/scope.nim:24` — `lookupFor(scope)` mengembalikan `some(scope.scopeId)` **hanya** untuk
  tipe scope pemanggil, `none` untuk lainnya.
- Pembaca nyata:
  - `infrastructure/auth_service.nim:50` `settingsOf` memakai `institutionScope()` → level
    `INSTITUTION` dengan id `""` (institusi akar). Ini yang membaca 6 key `platform.security.*`.
  - `infrastructure/calendar_repo.nim:36` `paramJson` memakai `scope` pemanggil (umumnya
    `institutionScope()` juga di jalur Fase 0); `calendar_repo.nim:77` `calendarShape`.
  - `infrastructure/param_source_db.nim:22` `dbParamSource.fetch` = adaptor port application.

Jadi scope yang diminta saat runtime Fase 0 adalah **`INSTITUTION:""`** (institusi akar), plus
kalender mengikuti `ScopeRef` pemanggil. `GLOBAL` selalu terlihat oleh resolusi.

### b. Aturan `missingActiveKeys` sekarang (lebih longgar)

`infrastructure/param_repo.nim:330`: `c.scopeType == scopeType and (scopeId.len == 0 or
c.scopeId == scopeId)`. Bila `scopeId` kosong, **setiap** kandidat di level itu dianggap memenuhi —
termasuk yang ber-`scope_id` konkret. `resolveCandidate` tidak begitu: `some("")` hanya cocok dengan
`scope_id` NULL. Itulah kelonggaran yang dilaporkan O-057.

Catatan penting: kekhawatiran "`GLOBAL` selalu memenuhi" **bukan** inkonsistensi — `resolveCandidate`
memang selalu mencocokkan `GLOBAL`. Yang tidak konsisten hanya **wildcard `scopeId` kosong**.

### c. Apakah ini dipanggil saat startup?

**Tidak (fakta, bukan asumsi).** `missingActiveKeys` disebarkan (grep seluruh repo) **hanya** ke
`modules/platform/tests/itparam.nim`; ia tidak dipanggil `apps/api/src/main.nim` maupun jalur
`serveApi`. Startup check spec §10.4 belum tersambung ke biner (sejalan dengan drift guard yang juga
baru dipakai di uji integrasi). Karena itu penyelarasan ini **tidak bisa** membuat deploy yang sehat
sekarang menolak start — tidak ada yang memanggilnya saat boot. Bila kelak disambungkan, 8 nilai
tersemai semuanya `GLOBAL`/NULL (`packs/base/generated/param_values.sql`), dan `GLOBAL` tetap
dianggap memenuhi oleh aturan baru → tetap lolos.

## Rencana

1. **Satu sumber kebenaran**: `missingActiveKeys` memakai `resolveCandidate` +
   `lookupFor(ScopeRef(scopeType, scopeId))`, bukan logika salinan. `GLOBAL` tetap selalu memenuhi
   (persis resolusi); `scopeId` kosong berubah dari wildcard menjadi "id kosong" yang sah.
2. **Uji pembeda aturan lama vs baru** di `itparam.nim`:
   - nilai hanya di `INSTITUTION:<id konkret>` sementara resolusi meminta institusi akar
     (`INSTITUTION:""`) → resolusi `none`; startup check **harus** melaporkan key hilang (aturan
     lama: lolos). Ini kasus inti O-057.
   - nilai hanya `GLOBAL` → tetap dianggap memenuhi level mana pun (konsisten dengan resolusi).
3. `./task check`, uji terdampak, lalu `./task ci`.

## Kriteria selesai (register)

> Uji: kasus yang tidak pernah "terlihat" oleh resolusi tidak dihitung aktif, dan sebaliknya;
> tidak ada kelonggaran tersisa

## Bukti

Perubahan:
- `modules/platform/infrastructure/param_repo.nim` — `missingActiveKeys` memakai
  `resolveCandidate(candidatesOf(...), lookupFor(ScopeRef(scopeType, scopeId)))`; import tambah
  `../domain/scope`.
- `modules/platform/tests/itparam.nim` — suite baru "param: startup check = visibilitas resolusi
  (O-057)" dengan 2 uji yang membedakan aturan lama vs baru.
- `modules/platform/MODULE.md` — invarian 8 menjelaskan definisi "aktif" startup check.

Bukti perintah (semua dijalankan di tree ini):

- **Uji pembeda aturan lama vs baru** — dengan fungsi **lama** dikembalikan sementara
  (`scopeId.len == 0` wildcard), `./task test itparam` **GAGAL** tepat di
  `[FAILED] nilai ber-id konkret tidak menyelamatkan pemanggil id kosong` (uji GLOBAL tetap `[OK]`).
  Setelah implementasi baru dipulihkan, keduanya `[OK]`. Jadi uji itu benar-benar memisahkan dua
  aturan, bukan sekadar ikut hijau.
- `./task check` **hijau** (format 109 berkas, `nim check` 110 berkas, archcheck, lint-nomagic,
  `paramgen --check`, i18n, `bash -n` 7 skrip).
- `./task test` **hijau**: **488 `[OK]`, 0 `[FAILED]`** (naik dari 486; +2 uji O-057).
- `./task ci` **hijau**: `488 [OK]`, 0 `[FAILED]`, e2e Playwright **23 lulus** (24.2 dtk; axe 2 tema ×
  2 locale), `== CI hijau`.

## Batas yang jujur

- `missingActiveKeys` **belum** dipanggil di jalur start biner; ini perbaikan kebenaran definisi,
  bukan perubahan perilaku deploy saat ini.
- Resolusi masih tinggal di `infrastructure` (D-034 butir 4 / T-016), jadi "satu sumber kebenaran"
  hari ini berarti `param_repo` memakai fungsi resolusi yang sama, bukan pindahnya logika ke
  `application`.
- `scopeId` untuk tipe non-GLOBAL tetap valid dengan id non-kosong; wildcard tidak diperkenalkan
  ulang (dilarang D-041/O-056).
