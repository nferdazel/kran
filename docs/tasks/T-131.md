# T-131 — Kontrak deploy & rilis: flock, retensi image/dump, pnpm pin, rollback gate, unit order, KEK doc, klaim spec

Status: **selesai** 24 Okt 2026. Sumber: audit 24 Okt 2026 OPS-1…OPS-10.

## Masalah

1. **OPS-1.** `flock` gagal → `exit 0`. Webhook melihat "sukses" padahal commit itu tidak pernah
   di-deploy; produksi tertinggal dari `main` tanpa sinyal apa pun.
2. **OPS-2.** `prune_images` hanya memangkas tag `^localhost/kran-api:[0-9a-f]{12}$`, padahal build
   tidak pernah membuat tag SHA. Kode mati; setiap deploy meninggalkan satu image tanpa tag.
3. **OPS-3.** Tidak ada `packageManager`; CI memakai `version: 11`, deploy memakai `corepack pnpm`
   tanpa versi. pnpm lama mengabaikan `minimumReleaseAge`/`allowBuilds` — kebijakan supply chain
   justru dilewati di jalur produksi.
4. **OPS-4.** Auto-rollback tidak memeriksa `/readyz` lagi; rollback yang gagal tetap dilaporkan
   sebagai "rollback selesai".
5. **OPS-5.** `sync_units` berjalan **sebelum** FREEZE/MIGRATION gate: `die` meninggalkan unit baru
   di disk, dan `daemon-reload`/reboot berikutnya bisa menjalankannya di image lama.
6. **OPS-6.** Contoh env memberi path **host** untuk KEK, padahal unit me-mount ke
   `/run/secrets/kran-kek.key` — mengikuti contoh itu membuat container exit 2.
7. **OPS-7.** Dump pra-deploy/pra-contract tanpa retensi.
8. **OPS-8.** Spec §21.7 mengklaim kompensasi yang tidak ada: base image dipin digest, tag `:<sha>`,
   `releases/<sha>/`.
9. **OPS-9.** Base image tidak dipin digest; tarball Nim diunduh tanpa verifikasi checksum.
10. **OPS-10.** Webhook hanya memeriksa HMAC (yang menutup **body**, bukan waktu kirim): tidak ada
    filter event/repo, tidak ada perlindungan replay.

## Yang diubah

- **OPS-1** — `flock` gagal → log ERROR + `exit 1`.
- **OPS-2** — `prune_images` (regex SHA) diganti `prune_previous_image`: ID image yang **sekarang**
  memegang `:prev` dicatat sebelum rotasi, dihapus setelah health gate sukses. `:local`/`:prev`
  tidak pernah disentuh; retensi tetap satu aktif + satu cadangan.
- **OPS-3** — `"packageManager": "pnpm@11.25.0"` di `package.json`; `version:` dihapus dari
  `pnpm/action-setup@v4` (action membaca `packageManager`); deploy membaca versi dari
  `package.json` dan batal (`die`) bila tidak ada.
- **OPS-4** — setelah rollback, `/readyz` dipoll ulang (15×2 dtk); dua keadaan dicatat berbeda
  ("rollback sehat, deploy gagal" vs "rollback juga tidak sehat, butuh intervensi").
- **OPS-5** — `sync_units` dipindah ke setelah gate, tepat sebelum restart.
- **OPS-6** — `ops/env/kran-prod.env.example`: nilai container = `/run/secrets/kran-kek.key`, dengan
  catatan bahwa perintah di host memakai path host.
- **OPS-7** — `backup-pre-deploy.sh`: retensi `KRAN_PREDEPLOY_KEEP` (default 10), dijalankan setelah
  dump baru lolos `pg_restore --list`.
- **OPS-8/OPS-9** — `apps/api/Dockerfile`: `FROM debian:bookworm-slim@sha256:7ff6ba…` (build + runtime
  stage) dan verifikasi `sha256sum` tarball Nim
  (`7df1611…`). Spec §21.7 dikoreksi: kompensasi yang benar-benar ada = digest, checksum, `.deployed_rev`,
  dan manifest satu baris `$APP_DIR/releases.txt` (rev, image ID, sha256 biner gate, waktu). Tag
  `:<sha>` dan `releases/<sha>/` **tidak** dibuat (kontrak emas §3.4 + retensi); deviasinya dicatat
  di `docs/ACCEPTED-LIMITS.md` (D-143).
- **OPS-10** — `hook.kran.json.example`: `trigger-rule` `and` = HMAC + `X-GitHub-Event: push` +
  `repository.name = kran`; replay ditutup di skrip: rev yang sama dengan `.deployed_rev` di-skip
  (`KRAN_FORCE_DEPLOY=1` untuk deploy ulang yang disengaja).

## Bukti

- `bash -n` untuk `deploy-vps.sh` dan `backup-pre-deploy.sh` → bersih.
- `./task check` → `ok: 8 scripts passed bash -n + shellcheck (warning level)` (termasuk kedua skrip

- Digest base image diambil dari Docker Hub (`library/debian`, tag `bookworm-slim`, 21 Okt 2026) dan
  checksum Nim dari `https://nim-lang.org/download/nim-2.2.12-linux_x64.tar.xz.sha256`.
- `./task build` → hijau (binary tidak berubah oleh batch ini; dijalankan sebagai pemeriksaan).

## Catatan / sisa

- Perilaku skrip **belum** diuji di server (tidak ada akses VPS dari sesi ini). Yang bisa dibuktikan di
  repo: sintaks, shellcheck, urutan langkah, dan konsistensi dengan kontrak emas. Verifikasi nyata
  terjadi pada deploy berikutnya (log langkah `skip`/`prune`/`releases.txt`).
- Build belum reproducible (tanpa lockfile Nim) — dicatat di `docs/ACCEPTED-LIMITS.md`, bukan
  diklaim selesai.
- Replay protection berbasis rev, bukan timestamp delivery: replay dengan rev yang sama di-skip,
  replay setelah rev baru tetap memicu deploy rev tersebut (yang memang isi `main`).
