# T-042 — Teardown in-process Mummy (O-025)

Status: DONE. Prioritas: P3. Titip: server HTTP → HUMAN-REVIEW-REQUIRED bila menyentuh jalur
shutdown. **Tidak menyentuh jalur shutdown produksi** — hanya harness uji + `close()`.

## Kenapa
`server.close()` pada harness test (Mummy 0.4.8 + ORC) dilaporkan pernah SIGSEGV. Shutdown
**produksi** sudah aman lewat jalur lain (T-024/D-031: sinyal → hentikan pump → `quit(0)`), jadi
sisanya = teardown in-process untuk uji.

## Recon
- `docs/spikes/O-025-shutdown.md`: probe 15 Okt — server minimal `close()` **tidak** crash; gejala
  bergantung konteks. Register O-025 menyebut "server hidup bersama pool DB + thread pump".
- `apps/api/src/server.nim` / `main.nim`: produksi **tidak** memanggil `server.close()`; `watchStop`
  memakai `quit(0)`.
- `apps/api/tests/{tapi,itapi,itapi_ws}.nim`: server dibangun di thread uji, disajikan thread lain,
  dan sengaja **tidak** ditutup (komentar menunjuk O-025).

## Rencana & hasil
1. **Reproduksi deterministik** (eksperimen kecil, berkas scratch dihapus) — **ter-repro**:
   `server.close()` SIGSEGV di `mummy.nim:1143` (`=destroy(server[])`) → `orc.nim
   nimDecRefIsLastCyclicDyn`/`unregisterCycle`. Variabelnya **thread**, bukan pool/pump/WebSocket:

   | Bangun server | `serve()` | `close()` dari | Hasil |
   |---|---|---|---|
   | thread uji | thread lain | thread uji | **SIGSEGV** |
   | thread uji | thread uji | thread lain | aman |
   | thread lain | thread lain | thread uji | aman |
   | thread lain | thread lain + WS hidup | thread uji | aman (3×) |

2. **Urutan aman:** bangun **dan** layani server di **thread yang sama**; `close()` dari thread lain
   (ia hanya memicu sinyal shutdown; `destroy` berjalan di thread pelayan, sama dengan tempat closure
   handler dialokasikan). Setelah `joinThread`, baru tutup pool.
3. **Uji:** `apps/api/tests/itapi_teardown.nim` (baru) menjalankan 2 siklus penuh dengan
   server + pool + pump nyata + klien WebSocket hidup, lalu teardown in-process secara penuh
   (`stopPump` → `server.close()` → `joinThread` → `pool.close()`), dan memeriksa port benar-benar
   bebas. Upgrade Mummy **tidak** diambil (pin `>= 0.4.8 & < 0.5.0`, D-037; belum ada bukti perbaikan
   hulu dari batas waktu ini) — dicatat sebagai sisa.

## Bukti
- Repro SIGSEGV: variabel "bangun di thread uji + `close()` dari thread uji" → proses mati
  (`mummy.nim:1143 destroy` → `orc.nim unregisterCycle`), diulang untuk pool/pump/WS mati/hidup.
- `./task test itapi_teardown` → 2 `[OK]`, 0 `[FAILED]`.
- `./task check` hijau; `./task test` **528 `[OK]`, 0 `[FAILED]`**; `./task ci` hijau (e2e 23 lulus).

## Sisa jujur
- `Server` yang sudah di-`close()` menjadi pointer menggantung — jangan dipakai lagi setelahnya
  (Mummy `deallocShared` objeknya; bukan salah ORC). Diuji hanya sampai "port bebas".
- Upgrade Mummy belum diambil: memerlukan keputusan terpisah (D-037) dan verifikasi tidak ada regresi
  dua sifat non-publiknya (D-037/O-049).
- Berkas ini **tidak** menyentuh jalur shutdown produksi; `main.nim`/`watchStop` tidak berubah.
