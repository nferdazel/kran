## Scope

`scopeAllows` now translates the subscriber's `EventScope` into a `ScopeFilter` and asks
`mayReadScope` — the same rule `GET /api/v1/params` uses — instead of special-casing `BRANCH` and
letting every other scope type through. Consequences, all of them the HTTP rule:

| `scope_type` | Delivered to |
|---|---|
| `GLOBAL` | any subscriber holding at least one `platform.param.read` grant |
| `INSTITUTION` | subscribers with an unbranched grant only |
| `BRANCH` | subscribers whose grant covers that branch, or unbranched |
| `PRODUCT`, `SEGMENT`, `ROLE` | nobody (membership cannot be evaluated, so it fails closed) |

An event whose `scope_type` is missing or unknown is also closed: a `param.changed` that cannot be
evaluated is dropped rather than broadcast. Every producer in this repo writes `scope_type`
(`param_repo.submitChange`/`approveChange`), so no real event is affected; two integration fixtures
that published `param.changed` without one were corrected to carry it.

Deliberately not changed: topic authorization, resume/replay plumbing, and which events are
produced. The replay path shares `scopeAllows`, so refused history is refused on reconnect too.

## Acceptance

A teller-scoped subscriber receives an `INSTITUTION` `param.changed` event (status `PENDING`) **only**
if it holds an unbranched grant. Proven at the hub (`trealtime`) and over a real WebSocket
(`itapi_ws`).
