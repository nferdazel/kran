## Scope

1. **Password denylist.** `passwordProblems` gains `ppTooCommon` and rejects any password whose
   lowercase form is an entry in `modules/platform/domain/password_denylist.txt`: every password the
   repo publishes in `packs/base/seed/*.sql`, plus a short list of the most common leaked passwords.
   The list is data in its own file rather than a Nim literal so `lint-nomagic` does not have to be
   loosened for digit-only strings and so a reviewer sees the whole list in one place.
2. **Seed accounts keep working.** Seeds write the hash directly and never call `passwordProblems`,
   so `./task dbtools seed --dev` is unaffected. The test proves this by logging in as `dev.maker`
   with the seed password throughout the existing suite.
3. **The guard survives a new seed.** `tauthz` walks `packs/base/seed/`, collects every file that
   writes `platform.app_user`, and fails if one is not in its known list, then asserts the published
   password is refused. Adding a seed account with a new password therefore breaks the gate until the
   denylist and that list are updated.
4. **Trusted proxy: one named gateway, no code default.** `identity.clientIpFrom` trusts
   `X-Forwarded-For` from loopback plus exactly the CIDRs in `KRAN_TRUSTED_PROXY_CIDRS`. The variable
   has **no default**: the `qouver` podman network is shared with sds-api and majadu-api, so a broad
   range would let a co-tenant reach this container's IP directly and forge the audit IP and the
   login bucket. The header is read **right to left**: the rightmost entry that is not itself a
   trusted proxy is the client. `KRAN_TRUSTED_PROXY_CIDRS=10.89.0.1/32` goes in
   `/srv/qouver/apps/kran/env/kran-prod.env`; `deploy-vps.sh` and the API start log both warn when it
   is empty, because the fail-closed state is safe but blind.
5. Deliberately not in scope: `Cf-Connecting-IP` at the Caddy layer. Caddy already runs with
   `client_ip_headers Cf-Connecting-IP X-Forwarded-For` and Cloudflare ranges in `trusted_proxies`
   (see `server/ops/caddy/Caddyfile.qouver1`), so the header the API receives from Caddy already
   carries the real client. The API does not read `Cf-Connecting-IP` directly and must not: nothing
   in front of the container sets it. **Unverified:** that the deployed Caddy block still carries
   those two lines, since the host was not reachable from here.
6. Deliberately not in scope: MFA parameters and enrolment, and the username change. Both stay with
   the owner as recorded in the closure note.

## Acceptance

- `passwordProblems(12, 1, "budi", "rahasia-panjang-123")` contains `ppTooCommon`, and the same
  value in upper case does too.
- `POST /api/v1/auth/password` with a real non-dev account and `rahasia-panjang-123` as the new
  password answers 400 `password_policy`; a normal long password on the same account answers 204.
- `clientIpFrom("10.89.0.1:41234", "198.51.100.7")` returns the gateway (no configured range: the
  shipped default is empty) and `clientIpFrom("10.89.0.1:41234", "198.51.100.7", gateway)` returns
  `198.51.100.7` where `gateway = initTrustedProxies("10.89.0.1/32")`.
- `clientIpFrom("10.89.0.9:41234", "198.51.100.7", gateway)` returns `10.89.0.9`: a co-tenant on the
  shared network is not the proxy.
- `clientIpFrom("127.0.0.1:1", "1.2.3.4, 198.51.100.7", gateway)` returns `198.51.100.7`; a forged
  left-hand entry does not win.

## Notes

- The denylist is deliberately a small, curated list rather than a full breached-password corpus: the
  list has to be readable in review, and the seed values are the ones that actually caused K-01.
- `KRAN_TRUSTED_PROXY_CIDRS` has **no code default** (K-02). The value must be set in
  `/srv/qouver/apps/kran/env/kran-prod.env`; `10.89.0.1/32` is the expected gateway and
  `podman network inspect qouver --format '{{(index .Subnets 0).Gateway}}'` confirms it on the host.
  Until it is set, the shipped behaviour is the old blind one: every client shares one limiter
  bucket and `client_ip` is the gateway. `deploy-vps.sh` and the API start log both warn, so the
  state is loud rather than silent.
- **Unverified from here:** the real podman subnet and gateway on qouver (the host did not resolve
  for an SSH probe), and whether the deployed `/etc/caddy/Caddyfile` still carries
  `client_ip_headers Cf-Connecting-IP X-Forwarded-For` with the Cloudflare `trusted_proxies` list.
  L-17's acceptance line stands: two real logins through `cbs.qouver.com` must show two distinct
  `platform.audit_log.client_ip` values, and neither may be the gateway.
- K-05 stays open by the reviewer's own instruction: `createUserWithRole` (`auth_service.nim:407`)
  and `bootstrapFirstAdmin` (`:444`) hash a caller-supplied password with no policy check, so only
  the CLI enforces the denylist today. Any future non-CLI caller inherits no denylist; that is a new
  task, not part of T-298.
- Reading the chain right to left changes one existing test expectation
  (`"[::1]:51515", "198.51.100.7, 10.0.0.1"` now resolves to `10.0.0.1`, the hop actually connected
  to our proxy). That entry was the leftmost, which is the spoofable end.
