Rangkaian kegagalan **nyata** di server (semuanya sudah diperbaiki + di-push; tidak satu pun tersentuh
gate lokal, karena gate tidak pernah menyentuh DB kosong, hook, atau host Rocky):

1. **Host tidak punya `libpq`** (Rocky 9), sedangkan biner dibangun di image Debian → `could not load:
   libpq.so(.5|)`. Memasang paket butuh root (tidak ada sudo tanpa password), jadi `deploy-vps.sh`
   mem-*vendor* lib dari image: `libpq.so.5`, `libldap-2.5.so.0`, `liblber-2.5.so.0`, `libsasl2.so.2`
   (nama tujuan = **soname**, karena `podman cp` mengikuti symlink). Unit memakai `LD_LIBRARY_PATH`.
   Kalau `libpq` kelak dipasang di host, blok vendor itu boleh dihapus.
2. **Deteksi perubahan rusak:** daftar fallback-nya satu baris dipisah spasi sedangkan grep-nya
   ber-anchor `^` → `^apps/api/` tidak pernah cocok, build API dilewati di deploy pertama. Juga `tools/`
   tidak termasuk pemicu rebuild padahal `dbtools/lib` dikompilasi ke biner.
3. **`reportStatus` gagal di DB baru:** `SELECT ... FROM platform.schema_migration` padahal tabelnya
   belum ada → deploy pertama mustahil lewat. Sekarang `migrationTableExists` diperiksa dan reportStatus
   tetap **read-only** (uji pembeda ada di `itplatform`).
4. **Gate migrasi salah arti:** `--check` keluar 1 untuk "tertunda" (normal saat deploy) *dan* "drift"
   (bahaya). Sekarang hanya drift yang membatalkan; keluaran tak dikenal = fail-closed.
5. **`pgcrypto` ayam-telur:** runner memakai `digest()` untuk checksum sebelum migrasi `0002` membuat
   ekstensinya → `bootstrapSql` sekarang memastikan `CREATE EXTENSION IF NOT EXISTS pgcrypto`.
6. **Guard dump terlalu kasar:** ambang 10000 byte menolak dump 2269 byte yang sah (DB dengan satu tabel
   kosong). Sekarang dinilai dari isi (`pg_restore --list` + daftar memuat definisi tabel).
7. **Jalur hook tidak punya env aplikasi:** `webhook.service` tidak mewarisi `EnvironmentFile` unit →
   `KRAN_DATABASE_URL kosong`. Sekarang `deploy-vps.sh` memuat `$APP_DIR/env/kran-prod.env` sendiri.
8. **Unit tidak meneruskan `--port`/`--address`:** biner **tidak** membaca `KRAN_PORT` (hanya flag),
   jadi app memakai default 8080 — yang di host ini sudah dipakai container lain → crash-loop
   `Address already in use`. Unit sekarang meneruskan `${KRAN_PORT}`/`${KRAN_BIND_HOST}`.

Catatan jujur: pada (8) asumsi saya sebelumnya — bahwa mengubah `KRAN_PORT` di env sudah cukup — **salah**;
peralihan tampak "sudah disiapkan" padahal port-nya tidak pernah benar-benar berpindah.

Sisa yang belum: `kran-worker` keluar 3 (peran worker belum ada → O-060), dan tidak ada berkas lock
dependensi (`kran.lock` → O-059).

## Peralihan domain — butuh root (langkah pemilik)
`/etc/caddy/Caddyfile` milik root dan tidak ada sudo tanpa password, jadi langkah ini tidak bisa
dijalankan otomatis. Urutan aman (rincian perintah ada di `docs/runbooks/deploy-setup.md` §F):
1. Hentikan container lama `cbs-api` (membebaskan 8095) → set `KRAN_PORT=8095` → restart `kran-api`.
2. Ganti blok `cbs.qouver.com` di Caddyfile dengan blok A `ops/caddy/Caddyfile.kran.example`
   (file_server dari `/srv/qouver/apps/kran/web` + `handle /api/*` → 8095) → `restorecon -RF` → validate
   → `systemctl reload caddy`.
3. Verifikasi `https://cbs.qouver.com` (halaman login + `/api/v1/auth/session`), lalu hentikan `cbs-web`.
Rollback: `podman start cbs-api cbs-web` + kembalikan upstream Caddy ke 3005.
