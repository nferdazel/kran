## Scope

Two day-close tasks, `platform.outbox_purge` and `platform.inbox_purge`, registered in
`daycloser_tasks.nim` (AGENTS §1.7: no cron of its own). Each reads its own retention parameter on
the business date, then deletes in `chunkSize` batches until a batch comes back short.

In scope:

- `outbox.completed_at` is written by `markDone` (always) and `markFailed` (only when the row lands
  on `DEAD`); `redrive` deliberately leaves it alone. Without this the purge deletes nothing, which
  is exactly what Adit flagged.
- Purge predicate: `status IN ('DONE','DEAD') AND completed_at < now() - retention`. `PENDING` and
  `IN_FLIGHT` are never touched, and a re-driven row is out of scope until it finishes again.
- Fail-closed: parameter missing or not an integer >= 1 makes the task `FAILED` with zero rows
  deleted. No default in code, no "skip quietly".
- `modules/platform/api.nim`: the composition root reaches the module through a public surface
  instead of a new `infrastructure/` import, so archcheck baseline stays at 498.

Out of scope, deliberately:

- Audit log, party/KYC and teller retention. Those tables physically refuse `DELETE`; audit needs
  archive-and-rotate with a chain baseline, which is T-302.
- Prod index strategy. `0105` uses plain `CREATE INDEX`; if prod `platform.outbox` is already above
  roughly a million rows, build both indexes with `CREATE INDEX CONCURRENTLY` before the deploy
  (`IF NOT EXISTS` makes the migration a no-op afterwards).
- The compliance sign-off in O-130. The 30 days are an engineering number, not a regulatory one.

## Rollback

Revert the purge commits and redeploy. Rows already deleted are past the D-206 window by
construction, so nothing that is still needed disappears; if the window itself turns out wrong, the
fix is the parameter value (a parameter change, maker-checker), not a code revert.
