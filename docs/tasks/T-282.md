## Scope

Two day-close tasks, `platform.outbox_purge` and `platform.inbox_purge`, registered in
`daycloser_tasks.nim` (AGENTS §1.7: no cron of its own). Each reads its own retention parameter on
the business date, then deletes in `chunkSize` batches until a batch comes back short.

In scope:

- `outbox.completed_at` is written by `markDone` (always) and `markFailed` (only when the row lands
  on `DEAD`); `redrive` deliberately leaves it alone. Without this the purge deletes nothing, which
  is exactly what Adit flagged.
- Purge predicate: `status IN ('DONE','DEAD') AND completed_at < now() - retention`. `PENDING` and
  `IN_FLIGHT` are never touched, and a re-driven row is out of scope until it finishes again.
- Fail-closed: parameter missing or not an integer >= 1 makes the task `FAILED` with zero rows
  deleted. No default in code, no "skip quietly".
- `modules/platform/api.nim`: the composition root reaches the module through a public surface
  instead of a new `infrastructure/` import, so archcheck baseline stays at 498.

Out of scope, deliberately:

- Audit log, party/KYC and teller retention. Those tables physically refuse `DELETE`; audit needs
  archive-and-rotate with a chain baseline, which is T-302.
- Prod index strategy. `0105` uses plain `CREATE INDEX`; if prod `platform.outbox` is already above
  roughly a million rows, build both indexes with `CREATE INDEX CONCURRENTLY` before the deploy
  (`IF NOT EXISTS` makes the migration a no-op afterwards).
- The compliance sign-off in O-130. The 30 days are an engineering number, not a regulatory one.

## Acceptance

Findings:

- MAJOR `modules/platform/infrastructure/retention_repo.nim:44-53` (`DELETE` qual on line 53) — the purge predicate lives
  only in the `doomed` CTE; the `DELETE`'s own qualification is `o.outbox_id = d.outbox_id`, so a
  row that a concurrent redrive has just moved to `PENDING` is still deleted. This falsifies the
  comment at lines 41-42 and the scope sentence "a re-driven row is out of scope until it finishes
  again". Reproduced on `kran_t282_test` with the exact statement from the repo: session A
  `BEGIN; UPDATE … SET status='PENDING' WHERE status IN ('DEAD','IN_FLIGHT'); pg_sleep(3);
  COMMIT;`, session B the purge statement — A reports `UPDATE 1` and `COMMIT`, B reports
  `DELETE 1`, and the row is gone. The operator's redrive therefore succeeds and the event is
  never re-sent, with no error anywhere. Fix (one clause, verified): add the predicate to the
  `DELETE` qual so it is re-checked against the updated tuple —

  ```sql
  DELETE FROM platform.outbox o
   USING doomed d
   WHERE o.outbox_id = d.outbox_id
     AND o.status IN ('DONE', 'DEAD')
  ```

  With that clause the same race returns `DELETE 0` and the row survives as `PENDING`.
  `purgeInbox` needs no equivalent change: inbox rows are never updated, so `ctid` holds for the
  life of the statement.

- MINOR `apps/api/src/daycloser_tasks.nim:159-160` — nothing fails if the two `reg.register`
  lines are deleted. Both retention suites build the task through `outboxPurgeTask(pool)` /
  `inboxPurgeTask(pool)` directly, so the wiring that makes the purge actually run in a day-close
  is untested; the capability would silently become a no-op. Fix: after `registerDayCloseTasks`,
  assert `reg.contains(outboxPurgeTaskId)` and `reg.contains(inboxPurgeTaskId)`.

- MINOR `modules/platform/migrations/0105_platform_outbox_inbox_purge_indexes.sql:31-34` — the
  header documents the `CONCURRENTLY` caveat for the two indexes but not the backfill: the
  `UPDATE … SET completed_at = now()` writes a new tuple version for every `DONE`/`DEAD` row, in
  one transaction, with no batching. Same production condition the index note names (outbox above
  roughly a million rows) makes this a long lock-holding statement. Fix: say so next to the
  `CONCURRENTLY` paragraph, or batch the backfill outside the runner like the index.

- MINOR `modules/platform/infrastructure/retention_repo.nim:63-71` — `purgeInbox` deletes by
  `ctid`, justified in the comment as "walau tabel tidak punya primary key tunggal", but
  `platform.inbox` has `PRIMARY KEY (consumer, event_id)` (`0003_platform_outbox_inbox.sql:48`).
  No proven bug (inbox rows are never updated, and the CTE and `DELETE` share one snapshot), but
  `ctid` buys nothing here and cannot re-check a predicate. Fix: delete on `(consumer, event_id)`.

D-207: it contradicts nothing I would veto. My sign-off on `audit_verify()` in T-302 is
