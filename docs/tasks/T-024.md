# T-024 — Shutdown bersih (O-025)

Status: DONE (bukti di bawah)

## Kenapa
`server.close()` SIGSEGV (Mummy 0.4.8 + ORC). Akibatnya restart/deploy tidak bisa diandalkan tanpa
SIGKILL, dan jalur "berhenti dengan tenang" tidak bisa dibuktikan — fondasi ops yang rapuh.

## Rencana
Berkas: `apps/api/src/main.nim` (+ spike singkat di `docs/spikes/` bila perlu).
Langkah: reproduksi minimal → tentukan batas masalah (Mummy vs ORC vs urutan penutupan) → pilih
jalan keluar terkecil (mis. urutan penutupan, hindari `close()` pada jalur produksi dengan alasan
tertulis, atau bounded-time wait) → buktikan dengan test yang **menjalankan biner** dan memeriksa
kode keluar.

## Kriteria selesai
- [ ] Reproduksi + analisis tertulis (spike) sebelum mengubah perilaku.
- [ ] Perilaku berhenti: sinyal → proses keluar bersih (kode 0), tanpa SIGSEGV, dalam batas waktu.
- [ ] Test otomatis yang memeriksa kode keluar; `./task ci` hijau.

## Hasil

- `apps/api/src/main.nim`: `onStopSignal` (hanya flag atomik) + `watchStop` (hentikan pump, batas 2
  detik, log, `quit(0)`), dipasang untuk `SIGINT` dan `SIGTERM`. `server.close()` tidak dipakai.
- `apps/web/tests/e2e/shutdown.spec.ts`: spawn biner di port bebas, tunggu `/healthz`, kirim
  `SIGTERM`, harapkan `code = 0` + `signal = null` + log penutupan.
- `docs/spikes/O-025-shutdown.md`: fakta (tak ada penangan sinyal; dua proses sisa 16 jam; probe
  `close()` tidak crash) + keputusan + batasan.
- Keputusan: **D-031**. O-025 diperkecil (teardown in-process), batas baru **O-047** (tanpa drain).
- Mutasi: penangan sinyal dilepas → spec GAGAL; dikembalikan → lulus (3,7 detik).
