# T-041 — `/readyz` memeriksa migrasi & lag outbox (O-019)

Status: READY. Prioritas: P2. Titip: jalur deploy (health gate) → perhatikan rollback.
Keputusan terkait: D-043 (peralihan di tempat, health gate di 8095), D-040 (migrasi dua tahap).

## Kenapa
`ops/scripts/deploy-vps.sh` memakai `/readyz` sebagai health gate + auto-rollback (spec §21.4 #11).
Hari ini `/readyz` hanya memeriksa DB, pump realtime, dan status drain — **belum** migrasi tertunda dan
**belum** lag outbox. Artinya deploy bisa dinyatakan sehat padahal skema belum lengkap atau outbox
menumpuk.

## Fakta dari kode (recon 16 Okt 2026)
- `apps/api/src/readiness.nim`: probe yang ada = `databaseProbe`, `realtimeProbe`, `drainProbe`,
  `combineProbes`.
- `apps/api/src/main.nim` sudah memuat `roleMigrate` dan mengimpor `dbtools` (jadi logika migrasi bisa
  dipakai ulang tanpa duplikasi).
- T-035 menambah `pendingExpand`/`contractPending`/`destructivePending` di `tools/dbtools/lib.nim`.

## Rencana
1. Probe migrasi: gagal bila ada migrasi **expand** tertunda (contract/destructive tidak dihitung —
   sama seperti `--check`, D-040).
2. Probe outbox: gagal bila ada baris belum terkirim lebih tua dari ambang; ambang dari parameter
   (bukan literal di kode) atau konstanta teknis ber-komentar bila parameter memang belum ada.
3. `/readyz` mengembalikan 503 + detail probe yang gagal; `/healthz` tetap tidak menyentuh DB.
4. Test: unit untuk logika probe; integrasi HTTP untuk 200/503.

## Kriteria selesai
- [ ] `/readyz` 503 saat migrasi expand tertunda; 200 saat bersih (dibuktikan test, bukan klaim).
- [ ] `/readyz` 503 saat outbox menumpuk melewati ambang.
- [ ] Tidak ada nilai bisnis baru di kode (`lint-nomagic` hijau); `./task ci` hijau.
