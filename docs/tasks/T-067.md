# T-067 — Layanan API/worker KRAN sebagai container quadlet

Status: **DONE** (19 Okt 2026). Keputusan: **D-066** (permintaan pemilik; dikerjakan lewat sesi
terpisah, didokumentasikan + diaudit di sesi ini).

## Kenapa

Aplikasi lain di VPS berjalan sebagai container quadlet; KRAN masih biner native + dua systemd user
unit. Pemilik meminta KRAN mengikuti pola yang sama agar operasinya seragam. Ini juga menutup kelas
masalah "repo dan produksi berbeda tanpa ada yang tahu": unit native hanya berubah kalau disalin
tangan.

## Scope

- `apps/api/Dockerfile`: image runtime berisi biner + `libpq5`/`libpcre3`, user `kran` (uid 10001).
- `ops/systemd/kran-{api,worker}.container`: unit quadlet (image, network `qouver`, port, mount
  `modules/`, `Exec` per peran).
- `ops/scripts/deploy-vps.sh`: `sync_units`/`restore_units` untuk `*.container`, penjaga fail-closed
  terhadap unit native bernama sama, rollback lewat tag image.
- `ops/systemd/superseded/*.service`: unit native lama, dipindah agar tidak bisa terpasang lagi.
- `docs/spec/kran-prd-techspec.md` §21.5/§21.6: ditandai digantikan D-066.
- `docs/runbooks/deploy-setup.md`: amandemen §D2.
- `docs/ACCEPTED-LIMITS.md`: baris `--root`, KEK, penumpukan image.

## Bukti (produksi, 19 Okt 2026)

```
systemctl --user is-active kran-api kran-worker   -> active / failed (exit 3, by design)
podman ps (grep kran)                             -> kran-api Up, 127.0.0.1:8095->8095/tcp
podman inspect (networks)                         -> qouver, 10.89.0.31/24
curl 127.0.0.1:8095/readyz                        -> {"status":"ok"} database/migrations/realtime ok
tail deploy.log                                   -> aafc715: "API sehat"; "Deployment completed successfully"
```

- Unit terpasang identik dengan repo → `sync_units` berjalan sebagai no-op.
- Berkas native tersisa sebagai `*.disabled` / `*.reinstalled-20261019`; tidak ada
  `kran-api.service` di `~/.config/systemd/user`.
- `systemctl --user is-enabled kran-api` = `generated` — normal untuk quadlet; boot tetap jalan karena
  generator membuat `/run/user/1001/systemd/generator/default.target.wants/kran-api.service`.

## Insiden yang ditemukan saat cutover

Deploy pertama setelah cutover (19 Okt 2026) me-restart **biner lama**: symlink
`~/.config/systemd/user/default.target.wants/kran-api.service` + berkas unit native masih ada, dan
unit native menang atas unit generator dengan nama sama. Health gate membaca biner lama itu juga,
jadi deploy melaporkan sukses tanpa perubahan. Perbaikan: unit lama dipindah ke
`ops/systemd/superseded/` dan deploy kini **menolak** jalan bila unit native bernama sama ada.

## Sisa jujur

- Tag image menumpuk satu per deploy (26 tag ≈ 2,4 GB apparent pada 19 Okt 2026) → **T-069**.
- `KRAN_KEK_FILE` belum di-mount; mengaktifkannya butuh mount + `UserNS=keep-id:uid=10001,gid=10001`
  (dicatat di unit + `ACCEPTED-LIMITS`; terkait O-071).
- `kran-worker` tetap exit 3 sampai perannya ada (O-013/O-060) — bukan regresi.
- Rollback manual belum pernah dijalankan di produksi (hanya harness); latihan tetap pekerjaan
  terpisah (T-013).
