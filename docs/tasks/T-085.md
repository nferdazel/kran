# T-085 — O-072b: wajibkan Idempotency-Key di endpoint rentan

## Lingkup

Memasang helper T-084 di tiga endpoint pembuat objek (D-098): `POST /parties`,
`POST /parties/{partyId}/risk-rating`, `POST /params/{key}/changes`. Header wajib; replay 200 +
`Idempotent-Replayed: true`; kunci sama dengan isi/operasi beda → 409. Klaim in-flight (409 +
`Retry-After`) tetap dipetakan tetapi bersifat defensif: dengan klaim+penutupan satu transaksi baris
itu tidak muncul (D-117).

## Perubahan

### HTTP util

- `respondJsonHeaders(req, status, body, extra)` di `apps/api/src/http_util.nim` supaya replay
  bisa menambahkan `Idempotent-Replayed` tanpa menduplikasi header content-type.

### Handler

Pola yang sama di ketiga handler:

1. Parse body seperti sekarang (`node`).
2. Header wajib: `Idempotency-Key` tidak ada **atau** kosong → 400 (`idempotency_key_required`).
   Untuk `param` memakai `respondParamReason` dengan `params.reason`; party/KYC memakai
   `respondProblem`.
3. Bungkus isi transaksi dengan `withIdempotency(db, principal, req, operationId, $node, asOf,
   app.clock.now(), body)`. `asOf = businessDateIso(app.clock)` dihitung sebelum transaksi.
4. `body()` mengembalikan `(status, payload)` hanya untuk sukses (2xx). Semua jalur error tetap
   `raise` seperti sekarang → klaim ikut rollback (D-098).
5. Peta hasil:
   - `idemProceed` → status/payload asli.
   - `idemReplay` → 200 + `Idempotent-Replayed: true` + payload tersimpan.
   - `idemMismatch` → 409 `idempotency_key_conflict`.
   - `idemInFlight` → 409 + `Retry-After: <detik>` (defensif, D-117; helper membatasi 60 detik).
6. `IdempotencyConfigError`/`IdempotencyStateError` → 500 (bukan 400).

Operation ID:
- `party.create`
- `party.risk.change`
- `param.submit`

### Kontrak

- Tiga operasi POST mendapat parameter header wajib `Idempotency-Key`
  (`minLength: 1`, `maxLength: 200`).
- Respons **200 (replay)** memuat header `Idempotent-Replayed: true`; 201 tidak memuat header
  ini (kontrak tidak mendeklarasikannya).
- Respons 409 didokumentasikan untuk ketiga operasi.
- Regenerasi klien TS lewat `./task openapi`.

### Test

- `itapi_party`: kirim kunci unik pada setiap POST (helper test), plus test replay (200 + header +
  tidak ada party/audit kedua), konflik isi (409), tanpa kunci (400).
- `itapi_kyc`: idem untuk risk-rating; replay tidak menambah baris `risk_assessment`/audit/event.
- `itapi_fase1` (param submit): replay tidak menambah `param_value`; konflik isi 409; tanpa kunci 400.
- Contract test: header wajib + 409 terdokumentasi.
- Mutation check: hapus pemakaian helper di satu endpoint → test replay merah.

## Risiko / catatan

- **O-093 / D-118**: `response_body` menyimpan respons apa adanya, termasuk `displayName`. Pemilik
  memilih penerimaan risiko untuk pilot (**D-118**, 22 Okt 2026): hanya DB, tanpa log, retensi
  mengikuti TTL + sapuan T-089. Sebelum produksi berisi data anggota nyata wajib masking/allowlist
  atau enkripsi kolom + retensi formal, ditandai `HUMAN-REVIEW-REQUIRED`.
- Klien lama yang belum mengirim header akan gagal 400; UI saat ini belum memanggil endpoint ini,
  jadi tidak ada regresi UI.
- Replay mengembalikan 200 (bukan 201) sesuai D-098; klien harus memperlakukan keduanya sukses.
- Duplikat **konkuren** tidak dijawab 409: permintaan kedua menunggu unique index lalu replay
  setelah pemenang COMMIT (D-117). Baris in-flight ter-COMMIT tidak mungkin muncul dengan klaim
  satu transaksi, jadi `Retry-After` defensif. Kontrak menulis 409 untuk konflik isi/operasi.
- Sidik jari dihitung dari `$node` (JSON hasil parse), jadi spasi/format ulang tidak mengubah
  identitas, tetapi **urutan kunci** dan nilai tetap harus sama. Klien yang mengubah isi body saat
  retry akan menerima 409 — perilaku yang diinginkan.
