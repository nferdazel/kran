# T-130 — Ketahanan HTTP: errorHandler + PoolError, worker/pool, N+1, XFF, access log

Status: **selesai** 24 Okt 2026. Sumber: audit 24 Okt 2026 API-1, ARC-1, ARC-2, SEC-2, API-6.

## Masalah

1. **API-1.** `router.errorHandler` tidak pernah dipasang; handler hanya menangkap `DbError`. `PoolError`
   (timeout ambil koneksi, koneksi mati, deadline) lolos ke Mummy → **500 tanpa badan dan tanpa log**.
2. **ARC-1.** Mummy memakai `countProcessors() * 10` worker (40 di 4 vCPU) sementara pool 8 koneksi:
   lebih dari 8 permintaan ber-DB hanya mengantre 5 detik lalu gagal. Probe `/readyz` membuat pool
   sendiri, jadi hijau walau pool permintaan penuh.
3. **ARC-2.** N+1: `authorizedAtBranch` (2–3 query) dipanggil per baris rekening (≤200), dan
   `userJson` menjalankan satu query role per pengguna.
4. **SEC-2.** `X-Forwarded-For` dipakai apa adanya untuk kolom `inet` audit dan kunci pembatas login:
   bisa dipalsukan klien, dan satu nilai ngawur membuat penulisan teraudit gagal 500.
5. **API-6.** Tidak ada access log per permintaan (method, rute, status, durasi, traceId).

## Yang diubah

- **API-1** — `router.errorHandler` di `server.nim`: `PoolError` → `503 SERVICE_UNAVAILABLE`
  (`params.reason = pool_unavailable`, `Retry-After: 1`) dan log; exception lain → 500 problem+json
  dengan `detail` tetap, sebabnya hanya ke log. `pkUnavailable` ditambahkan; i18n
  `error_service_unavailable` (id/en) + pemetaan `errors.ts`.
- **ARC-1** — `AppContext.serverThreads`, diisi `max(1, poolSize - 1)` (satu koneksi untuk pump
  LISTEN); `newApiServer` meneruskannya ke Mummy. `databaseProbe(sharedPool)` memakai pool proses
  (`/readyz` ikut merah bila pool bermasalah); probe tanpa argumen tetap membuat pool sendiri untuk
  test/konstruksi awal.
- **ARC-2** — `access.loadBranchAuthz` + `allowedAt` (satu muat grant + pasangan SoD per permintaan,
  keputusan tetap lewat `authorize` yang sama) dipakai daftar rekening per party;
  `auth_repo.roleGrantsForUsers` memuat role semua pengguna dalam satu query, `userJson` menerima
  grant sebagai parameter.
- **SEC-2** — `identity.clientIpFrom`: `X-Forwarded-For` hanya dipercaya bila koneksi dari loopback
  (Caddy/proxy Vite di host yang sama), isinya divalidasi `parseIpAddress`, panjang ≤ 45, selain itu
  jatuh ke alamat socket.
- **API-6** — `beginRequestScope` (status + trace id per permintaan, threadvar di `http_util`),
  `recordStatus` di semua helper respons, `respondRaw` untuk respons ber-header sendiri
  (`Set-Cookie`, 204). Pembungkus permintaan mencatat satu baris `accessLogLine` (method, rute,
  status, ms) dengan `trace_id` yang **sama** dengan amplop problem.

## Bukti

- `./task test tidentity` → 5 test `[OK]`: header dari non-loopback diabaikan, header sah dari
  loopback dipakai, header tidak sah/kepanjangan jatuh ke alamat socket, IPv6 berkurung dinormalkan.
- `./task test taccess_log` → `[OK]`: format satu baris (`GET /api/v1/params 200 12ms`), status tak
  dikenal `-`, `serverThreads` dipakai apa adanya.
- `./task test itapi` → `[OK]`: rute ber-DB dengan pool tertutup menjawab **503** `problem+json`,
  `Retry-After`, `code = SERVICE_UNAVAILABLE`, `params.reason = pool_unavailable`; log menampilkan
  `GET /api/v1/params 503 0ms` dengan `trace_id` yang sama dengan log error. `databaseProbe(pool
  tertutup)` = `csFailed`.
- `./task test tapi`, `tcontract`, `itapi_deposit`, `itapi_users` → hijau (jalur respons, kontrak, dan
  kedua daftar yang diubah tetap sesuai).
- `./task check`, `./task lint-web`, `./task build` → hijau.

## Catatan / sisa

- Kontrak belum mendeklarasikan `503` pada operasi mana pun; itu bagian **API-3** (T-133) yang
  memperluas pemeriksa kontrak + regenerasi klien. Untuk sekarang UI tetap aman karena
  `problemMessage` memetakan lewat `i18nKey`.
- `X-Forwarded-For` dipercaya berdasarkan loopback, bukan daftar proxy terkonfigurasi. Cukup untuk
  topologi sekarang (Caddy dan API di host yang sama); bila API dipindah ke host lain, daftar proxy
  tepercaya harus jadi konfigurasi eksplisit (D-142).
- Access log memakai status yang dicatat helper. Handler yang merespons tanpa helper akan tercatat
  `-` — bukan 200 palsu; itu juga sinyal ada jalur respons baru yang belum memakai helper.
