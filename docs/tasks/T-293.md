## Scope

**In scope**

1. `LoanSummary.partyName` (string) on the list response only. `handleListLoans` resolves names for
   the whole page with one batch query (`partyNames(db, ids)`), never one query per row. The list
   item is built by a new `loanListItemJson(loan, partyName)` so `loanJson` and the five payloads
   that use it (`apps/api/src/handlers_lending.nim:188, 275, 478, 1543, 1594`) keep their current
   shape; `LoanDetail` and the action results are deliberately unchanged.
2. `DataColumn.nowrap?: boolean` on `DataTable`, rendered as `kran-nowrap` on the `th`/`td`; the
   disbursed-date column sets it so "10 November 2026" cannot break into three lines.
3. Member column becomes `{ key: "partyName", secondary: "partyId" }` with `rowLines` on the loans
   table: name on the primary line (13/600), party UUID on the secondary line (11 muted), both
   single-line with ellipsis.
4. `--row-height-two` drops from `3.5rem` (56px) to `2.5rem` (40px). Loans is the only caller of
   `rowLines` today (`rg 'rowLines' apps/web/src` returns nothing else), so the token change has one
   visible effect.

**Out of scope**

- Searching or filtering by member name; the filter stays `partyId` (`loans_filter_party`).
- Party detail fields (`legal_name`, `birth_date`, `address`): masked and encrypted per D-112, never
  read here. Only `party.party.display_name` is exposed, which `handleListParties` already returns.
- Other screens' tables; no other screen passes `rowLines` today.
- T-292 copy (`loans_empty` split) and T-294 page-overflow work. If the page still overflows at 360
  afterwards, that is T-294's acceptance, not this ticket's.
- Sorting, pagination, and any write action on the list.

## Acceptance

1. `GET /api/v1/lending/loans` items carry `partyName` as a non-empty string for every loan whose
   party exists; the contract in `packages/contracts/openapi/kran-api.yaml` declares it required on
   `LoanSummary` and the generated client contains it. The integration case fails on the parent
   commit (field absent).
2. The list handler resolves names with one lookup for the page: `rg -n 'partyById' apps/api/src/handlers_lending.nim`
   shows the submit path only, and the new `partyNames` is called once outside the loop. Review
   rejects a per-row query.
3. At viewport 1440 and 360, DPR 1, light and dark: every `/app/loans` body row has a bounding height
   of at most 44 CSS px (target 40); the committed spec prints one JSON record per run with `route`,
   `theme`, `physicalWidth`, `rowHeight`, `headerHeight`, `pageOverflow`, mirroring
   `T-288-zoom.log`. Parent commit: `rowHeight` 70.0625px at 360; at 1440 the parent row was
   already 40px, so there the failing assertion is the date rule, not the height (see Evidence).
4. The disbursed-date cell renders on exactly one line at 1440 and 360: `getClientRects().length === 1`
   on the cell's text and `white-space` is `nowrap`. Parent commit: `white-space: normal` at both
   widths; at 1440 the date happens to fit one line, at 360 it wraps and the row grows to 70.0625px.
5. The member cell shows the name on the primary line and the party UUID on the secondary line; a
   seeded party with a 60-character name produces ellipsis (`scrollWidth > clientWidth`) and does not
   raise the row above 44px. Parent commit: one line, UUID only.
6. `packages/ui/tests/components.test.ts` proves `nowrap` adds `kran-nowrap` and that `rowLines` still
   emits primary + secondary spans only when the secondary field is non-empty.
7. `./task check-fast` green; `./task e2e -- loans` green; axe 0 violations on `/app/loans` at 1440
   and 360 in both themes; no i18n key added or renamed.

## Notes

- Why not add `partyName` to `loanJson`: that helper feeds five payloads including `LoanDetail`, the
  disburse result and the write-off result. One schema delta is cheaper than five, and the detail
  screen already knows its own party.
- Why a batch lookup: the list runs up to 50 rows; `partyById` per row is 51 queries, and the
  existing per-row branch filter already makes the response smaller than `limit`.
- The T-288 row-height numbers came from a spec that was deleted; this ticket commits its measurement
  spec so the next person can re-run it instead of trusting a log.
