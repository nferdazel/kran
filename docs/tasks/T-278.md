## Scope

Seed role-authentic users and use them instead of granting `platform_admin` on the fly:

- `dev.kasir` — teller/cashier role only, the actor for teller session, vault and deposit flows.
- `dev.maker` — `param_maker` only (already seeded).
- `dev.checker` — `param_checker` only (already seeded).

Then replace each in-test `platform_admin` grant with the fixture that already holds the permission
being exercised, so the suite proves the real authorization path rather than an all-powerful actor.

Two things stay untouched: assertions that are about `platform_admin` itself (in `itapi_users`,
`itapi_roles`, and the last-admin guard), and any test that asserts a denial. Deleting an assertion
to make a suite green is the exact failure this task exists to prevent.

Out of scope: changing role definitions in the RBAC catalogue, and adding dev users for roles no
suite exercises.

## Acceptance

1. `./task dbtools seed --dev` on a fresh test DB creates `dev.kasir`, `dev.maker`, `dev.checker`
   with exactly the roles listed above and no `platform_admin`.
2. `rg -n 'platform_admin' apps/api/tests` shows only the tests that are about that role, and each
   remaining occurrence is named in the report with one line saying why it is not a grant for
   convenience.
3. The ten suites above pass without any in-test `platform_admin` grant: `./task test
   itapi_deposit itapi_teller itapi_teller_sessions itapi_party itapi_kyc itapi_product
   itapi_lending itapi_lending_reports itapi_detail itapi_users` green, separate DB.
4. `./task test itapi_auth` still green, and `./task test itapi_teardown` green (the seed reset
   contract still holds).
5. The e2e assertion that a maker cannot approve still passes; it must not be relaxed.
6. Seed re-run is idempotent: applying it twice leaves the same grants.
