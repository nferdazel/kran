# T-086 — O-085: maker-checker versi produk (DRAFT → ACTIVE)

## Lingkup

Versi produk tidak lagi terbit saat submit. Submit membuat `DRAFT`; approve oleh operator berbeda
men-seal binding, menutup versi ACTIVE sebelumnya, menulis audit, dan menerbitkan
`ProductPublished`. Reject menutup draft tanpa event terbit.

Status: **RENCANA** (belum ada kode). Task ditandai `HUMAN-REVIEW-REQUIRED`.

## Keputusan yang harus diambil sebelum coding

1. **Status `REJECTED` tidak ada di D-099.** D-099 hanya menyebut `DRAFT|ACTIVE`, sedangkan task
   meminta reject. Usul: tambah `REJECTED` + `reason` sebagai amendemen D-099 (trigger lama
   melarang DELETE, jadi reject tidak bisa menghapus draft). Alternatif: reject hanya menulis
   audit — ditolak karena draft menggantung selamanya.
2. **`sealed` saat ini di-set ketika binding pertama masuk** (`0002_product_catalog.sql:149-166`).
   D-099 meminta seal saat approve. Perlu ganti trigger: binding hanya boleh masuk ke DRAFT,
   seal diisi saat approve/reject.
3. **`maker NOT NULL` berisiko saat deploy.** Proses lama yang masih berjalan akan insert tanpa
   `maker`. Pilihan: trigger `BEFORE INSERT` sementara `maker = coalesce(maker, published_by)`,
   atau tunda `SET NOT NULL` ke migrasi contract. Pilih salah satu sebelum migrasi dijalankan.
4. **`ACCEPTED-LIMITS.md` tidak punya entri produk/O-085**, padahal D-099 mengklaim freeze
   tercatat di sana. Catat ketidakcocokan; jangan mengarang entri baru.

Asumsi rencana: `maker` = pengaju, `checker` = penyetuju/penolak, `checker <> maker` juga untuk
reject; `published_at` tetap berarti waktu pencatatan (utang nama, dicatat di MODULE.md).

## Rencana perubahan

### Skema

- `modules/product/migrations/0003_product_version_approval.sql`: kolom
  `status/maker/checker/approved_at/reason`, backfill baris lama ke ACTIVE (maker = published_by,
  approved_at = published_at, checker sentinel pack reviewer, sealed = true), CHECK self-approval,
  CHECK status lengkap, EXCLUDE parsial hanya untuk ACTIVE (butuh header `-- dbtools:destructive`),
  trigger `guard_version_update`/`assert_version_has_bindings`/`assert_binding_open` diganti.
- `modules/platform/migrations/0022_platform_rbac_product_approve.sql`: permission
  `product.catalog.approve` + grant `platform_admin` (0021 sudah dipakai T-084).

### Domain / repo

- `modules/product/domain/product.nim`: enum status, `parseVersionStatus`, `canTransition`,
  `assertDistinctActors`.
- `modules/product/infrastructure/product_repo.nim`: filter ACTIVE pada `currentVersion` /
  `openVersion` / `closeVersion`; insert DRAFT; `versionById`, `lockProduct`, `approveVersion`,
  `rejectVersion`.

### HTTP

- `POST /api/v1/products/{code}/versions/{versionId}/approve` (`approveProductVersion`)
- `POST /api/v1/products/{code}/versions/{versionId}/reject` (`rejectProductVersion`)
- Izin `product.catalog.approve`, gerbang cabang institusi; 409 untuk `not_draft`,
  `self_approval`, `window_conflict`; reject tanpa `reason` = 400.
- `POST /products` dan `POST /products/{code}/versions` tetap 201, tetapi membuat DRAFT, tidak
  menutup versi lama, dan tidak menerbitkan event.
- Kontrak: `ProductVersion.status/approvedAt`, path baru, regenerasi klien TS (`./task openapi`).

### Test

- Unit: status/transisi/self-approval.
- `itproduct`: dua draft bertumpang tindih sah, approve/reject, seal, binding ke ACTIVE ditolak,
  approve kedua gagal, immutability `effective_to`.
- `itapi_product`: maker submit → checker approve; 403; self-approval 409; replay/duplikat 409;
  reject; event hanya saat approve; v2 menutup v1 setelah approve.
- `itapi_fase1`: urutan submit → approve sebelum klaim event.
- Mutation check: event kembali ke submit, filter ACTIVE dihapus, EXCLUDE penuh, self-approval
  constraint dihapus — masing-masing harus membuat test merah.
