# T-159 — Deploy menunggu CI (fail-closed) + lock berbatas waktu

**Status**: DONE (1 Nov 2026) · **Keputusan**: D-178 · **Deps**: T-157

## Kenapa

Push ke `main` memicu CI dan webhook **bersamaan**. Deploy karena itu selalu lebih dulu tiba, dan
tidak ada satu pun langkah yang memeriksa status commit yang sedang di-deploy. Selama ini "pipeline
hijau" hanya asumsi; kejadian 1 Nov 2026 (web build mati di host, web tertinggal 6 hari) lolos tanpa
sinyal. Selain itu `flock -n` membuang commit yang sah saat beberapa push datang beruntun.

## Scope

- `ci_gate <rev>` di `ops/scripts/deploy-vps.sh`, dipanggil setelah skip delivery duplikat dan
  sebelum langkah apa pun yang mengubah host.
- `CI_EXPECTED` = empat nama job `ci.yml`. Hanya `success` hijau (`skipped`/`neutral` = tidak
  berjalan), satu nama dinilai dari run terbaru, check hilang atau timeout = gagal.
- Perubahan dokumen (selain `docs/**`/`*.md`) dilewati karena CI juga tidak berjalan untuk path itu.
- Opsi: `KRAN_GITHUB_REPO` (default `nferdazel/kran`), `KRAN_GITHUB_TOKEN` (repo publik, token
  hanya menaikkan batas API), `KRAN_CI_WAIT_SECONDS` (default 900),
  `KRAN_SKIP_CI_GATE=1` (darurat, tercatat `WARN`).
- Lock: `flock -w "$KRAN_DEPLOY_LOCK_WAIT"` (default 900 dtk), gagal dengan pesan yang menyebut
  commit-nya.

## Bukti

- `bash -n` + `shellcheck -S warning` bersih (8 skrip).
- Harness pada payload nyata: SHA hijau `d6358a1` → `OK`; `{"check_runs":[]}` → `PENDING` untuk
  keempat nama; payload `failure` + `skipped` → `FAILED`; run lama hijau + run baru `in_progress`
  → `PENDING` (run terbaru yang menentukan).
- Poll bersyarat: permintaan kedua dengan `If-None-Match` atas SHA yang sama dijawab `304`, jadi
  menunggu 15 menit tidak menghabiskan batas 60 permintaan/jam saat `KRAN_GITHUB_TOKEN` kosong.
- `python3` dan `curl` tersedia di host deploy (diperiksa langsung).
- Di host deploy (1 Nov): gate pada SHA `747fcb4` ketika CI masih berjalan → menunggu lalu
  `ERROR: GERBANG CI: timeout 45s, masih menunggu: Nim (...), DB (...)`; setelah CI selesai →
  `==> GERBANG CI: semua check hijau` / `GATE PASSED`.
- Deploy produksi pertama yang memakai gerbang ini (`4c0bb4c`, rilis v0.1.1) menunggu **14m04s**
  dari anggaran 15 menit: Nim/Web/Security selesai lebih dulu, DB yang menentukan. Default
  `KRAN_CI_WAIT_SECONDS` karena itu dinaikkan ke 1800 supaya deploy tidak gagal karena waktu, bukan
  karena CI merah. `releases.txt` mencatat biner `d38ed733…` (berbeda dari `c0230813…`), dan
  `/healthz` melaporkan `0.1.1` — stempel versi benar-benar sampai ke produksi.
