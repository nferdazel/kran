## 1. Scope

Masuk:
1. `teller.teller_session`: buka/tutup, opening float, counted cash, expected cash, variance, status.
2. `teller.vault`: satu vault per cabang, saldo cache `numeric(24,4)`, berkurang saat buka, bertambah saat tutup.
3. `teller.cash_movement`: arus kas laci per sesi (dari transaksi tunai 088b).
4. API sesi: `POST /teller/sessions`, `POST /teller/sessions/{id}/close`, `GET /teller/sessions/current`.
5. RBAC `teller.session.{open,close,read}` + grant runtime schema `teller`.
6. Gerbang sesi pada `POST /teller/cash-transactions` (bagian 093b).

Tidak masuk: framework `daycloser`/EOD (Fase 3, spec §11.6), cetak (T-094/ADR-013), UI (088d),
limit kas/nominal (parameter belum ditetapkan pemilik, T-088 §8 butir 1), GL untuk kas teller
(PERLU KEPUTUSAN #1), top-up vault (T-107), rekap/daftar transaksi per sesi (088d/T-108).

## 2. Skema + nomor migrasi

`modules/teller/migrations/0001_teller_schema.sql` → `CREATE SCHEMA teller;` (tanpa tabel, aman di seq 1).

`modules/teller/migrations/0006_teller_cash.sql` (seq 6 > `platform/0006` + `deposit/0004`):

```sql
teller.vault(
  branch_id uuid PRIMARY KEY,                      -- tanpa FK: belum ada tabel cabang (preseden deposit/0003)
  balance numeric(24,4) NOT NULL DEFAULT 0 CHECK (balance >= 0),
  updated_at timestamptz NOT NULL)

teller.teller_session(
  session_id uuid PK, branch_id uuid NOT NULL,
  teller_user_id uuid NOT NULL REFERENCES platform.app_user(user_id),
  business_date date NOT NULL,
  status text NOT NULL DEFAULT 'OPEN' CHECK (status IN ('OPEN','CLOSED')),
  opening_float numeric(24,4) NOT NULL CHECK (opening_float >= 0),
  opened_at timestamptz NOT NULL, opened_by uuid NOT NULL REFERENCES platform.app_user(user_id),
  expected_cash numeric(24,4), counted_cash numeric(24,4), variance numeric(24,4),
  note text CHECK (note IS NULL OR length(note) <= 200),
  closed_at timestamptz, closed_by uuid REFERENCES platform.app_user(user_id),
  CHECK ((status = 'CLOSED') = (closed_at IS NOT NULL AND counted_cash IS NOT NULL
         AND expected_cash IS NOT NULL AND variance IS NOT NULL)),
  CHECK (variance IS NULL OR variance = counted_cash - expected_cash))

CREATE UNIQUE INDEX teller_session_one_open_uq
  ON teller.teller_session (branch_id, teller_user_id) WHERE status = 'OPEN';
CREATE INDEX teller_session_branch_date_idx ON teller.teller_session (branch_id, business_date);

teller.cash_movement(
  movement_id uuid PK,
  session_id uuid NOT NULL REFERENCES teller.teller_session(session_id),
  movement_type text NOT NULL CHECK (movement_type IN ('CASH_IN','CASH_OUT')),
  amount numeric(24,4) NOT NULL CHECK (amount > 0),
  transaction_id uuid NOT NULL REFERENCES deposit.transaction(transaction_id),
  business_date date NOT NULL, occurred_at timestamptz NOT NULL, created_by uuid NOT NULL,
  CONSTRAINT teller_cash_movement_transaction_uq UNIQUE (transaction_id))
```

- `teller.cash_movement` + `teller.teller_session` immutable untuk UPDATE/DELETE baris movement
  (pakai `ledger.reject_mutation()`, sudah ada sejak `ledger/0003`; preseden `deposit/0005`).
- **Tanpa `journal_id`** di kedua tabel: T-093 tidak memposting jurnal (PERLU KEPUTUSAN #1).
- `bank`/variance: `numeric` skala 4, dibandingkan eksak — aman untuk CHECK di atas.

`modules/teller/migrations/0007_teller_runtime_grants.sql` → pola `deposit/0008`: `DO $$` idempoten,
`GRANT USAGE ON SCHEMA teller` + `SELECT/INSERT/UPDATE/DELETE ON ALL TABLES IN SCHEMA teller`.
Alasan dipisah: `ON ALL TABLES` hanya mencakup tabel yang ada **saat itu** (bug 0006/0008);
migrasi teller berikutnya yang menambah tabel wajib migrasi grant sendiri.

`modules/platform/migrations/0025_platform_rbac_teller_session.sql` → 3 izin
(`teller.session.open`, `teller.session.close`, `teller.session.read`) + grant eksplisit ke

## 3. Aturan

| # | Aturan | Penegakan |
|---|---|---|
| R1 | Satu sesi `OPEN` per (teller, cabang) | partial unique index `teller_session_one_open_uq`; pelanggaran → 409 `session_already_open` |
| R2 | Buka butuh `openingFloat ≥ 0` dan vault cukup | `UPDATE teller.vault SET balance = balance - ? WHERE branch_id = ? AND balance >= ?`; 0 baris → 409 `insufficient_vault_cash`; tanpa baris vault → 409 `vault_not_configured` |
| R3 | `expected_cash = opening_float + Σ CASH_IN − Σ CASH_OUT` sesi itu, dihitung **setelah** baris sesi dikunci | `SELECT ... FROM teller.teller_session WHERE session_id=? FOR UPDATE` lalu agregasi `cash_movement` |
| R4 | `variance = counted_cash − expected_cash` (positif = kas lebih, negatif = kas kurang) | CHECK tabel + audit; **selisih bukan 409** |
| R5 | Sesi tidak bisa ditutup dua kali | status `CLOSED` + `FOR UPDATE`; close kedua → 409 `session_not_open` |
| R6 | Transaksi tunai setelah sesi tutup ditolak | 093b: gate di `handlers_teller.nim` (lihat §5) |
| R7 | `business_date` sesi = `businessDateFor(db, institutionScope(), asOf)` (sama dengan 088b, bukan UTC mentah) | handler; gate transaksi mencocokkan `business_date` sesi |
| R8 | Tutup menambah vault sebesar `counted_cash`, **bukan** `expected_cash` | `UPDATE teller.vault SET balance = balance + ?` — uang fisik yang masuk vault |
| R9 | Sesi lama (business_date lampau) tetap boleh ditutup; tidak membuka sesi baru otomatis | handler (tanpa cek tanggal tutup) |

## 4. Pertanyaan kunci: wajib sesi OPEN?

**`POST /teller/cash-transactions` = wajib sesi OPEN.** Tanpa sesi, `expected_cash` dan variance
tidak punya arti, dan spec §11.6 menuntut gate "semua sesi tutup & kas seimbang".

**`POST /teller/transfers` = tidak wajib (093b).** PB tidak menggerakkan uang fisik. Bila sesi OPEN
ada, `session_id`-nya boleh dicatat di event/audit, bukan di `deposit.transfer` (tanpa migrasi
deposit). PERLU KEPUTUSAN #3.

Urutan rilis yang diusulkan (menghindari "endpoint terkunci tanpa jalan membuka"):

| Tahap | Isi | Gate |
|---|---|---|
| **T-093a** | schema + tabel + grant + RBAC + API sesi + test. **Tanpa** enforcement. | `./task verify teller` hijau |
| **T-093b** | gate sesi di `handlers_teller.nim` + tulis `cash_movement` dalam tx yang sama + fixture `itapi_teller` | idem |
| **T-093c** (opsional) | gate PB + rekap per sesi (bila diputuskan) | idem |
| **088d** | UI: panel buka/tutup kas + transaksi | `./task e2e` |

Karena belum ada klien teller di produksi (temuan #8), 093a+093b **boleh satu PR dua commit**
(commit 1 = aditif, commit 2 = perilaku). Alternatif "deploy 093a dulu, tunda 093b" **ditolak**:
jendela itu membuat sesi bisa dibuka sementara transaksi mengabaikannya → variance rapor palsu.

Konsekuensi rollback/deploy:
- Skema murni aditif (tanpa contract) → binary lama tetap jalan; tidak ada entri
  `ops/migrations/contract-auto.txt`.
- Rollback binary ke `:prev` setelah 093b: transaksi tunai kembali tanpa sesi sementara sesi masih
  `OPEN` → `expected_cash` saat tutup tidak memuat transaksi jendela itu. Mitigasi: tutup semua sesi
  (atau rekonsiliasi manual) sebelum rollback; catat di `ACCEPTED-LIMITS` + runbook.
- Izin `platform/0025` yang tidak dipakai binary lama = tidak berbahaya (idempoten, tanpa FK kode).
- `variance` tidak menyentuh GL/vault selisih → rollback tidak meninggalkan jurnal yatim.

## 5. API

| Operasi | Endpoint | Izin | Sukses | 409 (`params.reason`) |
|---|---|---|---|---|
| `postTellerSessionOpen` | `POST /api/v1/teller/sessions` | `teller.session.open` @cabang | 201 `{sessionId,branchId,tellerUserId,businessDate,status:"OPEN",openingFloat,openedAt}` | `session_already_open`, `insufficient_vault_cash`, `vault_not_configured` |
| `postTellerSessionClose` | `POST /api/v1/teller/sessions/{sessionId}/close` | `teller.session.close` @cabang sesi | 200 `{sessionId,status:"CLOSED",businessDate,openingFloat,expectedCash,countedCash,variance,closedAt}` | `session_not_open` |
| `getCurrentTellerSession` | `GET /api/v1/teller/sessions/current?branchId=` | `teller.session.read` @cabang | 200 sesi + `expectedCash` berjalan (dihitung, bukan disimpan) | 404 `session_not_open` |

- `branchId` wajib di body open dan query `current` (penjaga `authorizedAtBranch`); tanpa "cabang
  default pelaku" — tidak ada konsep itu di repo.
- Nominal = string desimal (`Money.toDecimalString`), bukan number (D-097); `countedCash ≥ 0`.
- `Idempotency-Key` **wajib** pada open & close (D-098: operasi finansial — vault berubah atau
  status berubah; retry setelah timeout tidak boleh mendebit vault dua kali / menutup dua kali).
  Replay = 200 + `Idempotent-Replayed`; hash beda = 409. Kunci jurnal tidak dipakai (tidak ada jurnal).
- 404 close: `sessionId` tidak ada → 404; ada tapi `CLOSED` → 409 (keputusan: bedakan "tidak
  dikenal" dari "sudah tutup").
- Validasi (400): `openingFloat`/`countedCash` bukan desimal, negatif, `branchId` bukan UUID,
  `note` > 200.
- Audit: `teller.session.open`, `teller.session.close` (after-payload: float/expected/counted/variance).
- Outbox (non-akuntansi, **tanpa** header `accounting`): `TellerSessionOpened`, `TellerSessionClosed`
  (payload memuat variance) → dipakai UI realtime 088d & gate Fase 3.
- Satu `withDbTx` + `withIdempotency` per operasi; open = 5 statement, close = 5–6 (jauh di bawah
  deadline 20 s, D-065).

**Detail penting (093b): gate sesi harus DI DALAM blok `withIdempotency`,** bukan sebelum. Kalau di
luar, replay transaksi yang sah setelah sesi ditutup akan dijawab 409 `session_not_open` — replay
harus mengembalikan respons tersimpan.

## 6. Integrasi dengan 088b: `session_id` di mana?

**Pilih tabel gerbang di sisi teller, bukan kolom di `deposit.transaction`.**

| Opsi | Penilaian |
|---|---|
| **A. `teller.cash_movement(transaction_id UNIQUE FK deposit.transaction)`** (dipilih) | Expand-only; modul `deposit` tidak disentuh (088b beku); mapping 1:1 ditegakkan FK+UNIQUE; `deposit` tidak tahu konsep teller. |
| B. `deposit/0009` `ALTER TABLE deposit.transaction ADD COLUMN session_id` | Sah expand-only (nullable, seq 9 > teller/0006), tetapi menambah konsep teller ke modul deposit + migrasi modul lain untuk kebutuhan T-093 → melanggar pemisahan yang sudah dijaga 088c (D-124). |
| C. Tanpa tabel, hitung dari `deposit.transaction` + `branch_id` + jam | Tidak bisa membedakan sesi pagi/siang, tidak ada audit arus laci. Ditolak. |

Konsekuensi: `expected_cash` hanya benar bila **setiap** transaksi tunai menulis `cash_movement`.
Dijaga oleh: satu `withDbTx` di handler (093b) + test paritas `COUNT(cash_movement) =
COUNT(deposit.transaction CASH_*)` per sesi. Bila 093b absen, jangan operasikan sesi (lihat §4).
