## Contract

`GET /metrics`, `operationId: getMetrics`, no authentication, no cookie use. Response is
`text/plain; version=0.0.4; charset=utf-8`, Prometheus text format.

Exposure rule: the request is served only when the peer is loopback or a peer in
`KRAN_TRUSTED_PROXY_CIDRS`; anything else gets `403 FORBIDDEN`. The reason is the deployment, not
caution: the API container binds `0.0.0.0` and rootless podman forwards the port, so an operator
scraping from the host arrives from the bridge gateway (`10.89.0.1`), not from `127.0.0.1`. The
public path is closed twice: Caddy proxies `/api/*` only, and the example separate-API block answers
`403` for `/metrics`.

## Series

Process, from atomics (no I/O):

| Series | Type | Source |
|---|---|---|
| `kran_http_requests_total{code}` | counter | per-status-code counter in the request wrapper |
| `kran_http_request_duration_seconds` | histogram | 11 buckets, sum, count |
| `kran_http_requests_in_flight` | gauge | `drain.inFlightCount()` |
| `kran_auth_login_failures_total` | counter | `handleLogin` on `aoInvalidCredentials`/`aoLocked`/`aoInactive` |
| `kran_process_uptime_seconds` | gauge | `AppContext.startedAt` |
| `kran_metrics_scrape_errors_total` | counter | scrape that could not read the DB |

Database, one connection per scrape, three small reads:

| Series | Source |
|---|---|
| `kran_db_pool_connections{state}` | `DbPool.stats` (created, idle, in_use, leaked_tx) |
| `kran_outbox_events{status}` | `outbox_repo.countsByStatus` (one query, all statuses) |
| `kran_outbox_dead_events` | `worker_repo.deadEventCount` |
| `kran_worker_heartbeat_age_seconds` | `worker_repo.workerHeartbeatAgeSeconds` |
| `kran_dayclose_open_runs` | `daycloser.run` state not `COMPLETED`/`CANCELED` |
| `kran_dayclose_last_run_duration_seconds`, `..._finished_timestamp_seconds` | last finished `daycloser.run` |

A DB failure does not fail the scrape: the process series still render, the DB block is omitted, and
`kran_metrics_scrape_errors_total` increments. A metrics endpoint that goes dark because the
database is down removes the one signal that says so.

No path label on the request counter: an unbounded label is a cardinality leak, and the access log
already carries method, path, status and duration per request.

Login failures are an in-process counter, not a `platform.audit_log` query: a scrape must not add
database load, and Prometheus handles a counter reset on restart through `rate()`. `aoMfaRequired`
is not counted - the password was right, the second factor was missing.

The database reads live behind two seams the app layer already owns: `readiness.outboxWorkerMetrics`
(that module already imports `outbox_repo`/`worker_repo` for `/readyz`) and
`daycloser_ctl.closeRunMetrics` (that module already imports `run_repo`). The handler module
therefore imports no module internals, which keeps `archcheck` at baseline 498 with no new entry and
no escape hatch.

## Acceptance

1. `GET /metrics` returns 200 with `text/plain; version=0.0.4; charset=utf-8`, `security: []` in the
   contract, and the route is declared on both sides (contract test green).
2. The request counter and the histogram move after a real request; a 4xx/5xx response is counted
   under its own code, so error rate per code is derivable.
3. A scrape with the database unreachable still returns 200, omits the DB series, and increments
   `kran_metrics_scrape_errors_total`.
4. A peer outside loopback and outside `KRAN_TRUSTED_PROXY_CIDRS` gets 403.
5. `./task check-fast` green; `./task verify api` green.

## Open

1. **No alerting.** Spec §7.5 also asks for alerts (readiness failure, stale heartbeat, dead events,
   failed close, anchor age, disk pressure). This task exposes the series; a rule file and a
   receiver are host work and belong to a separate task with Arif.
2. **No dashboard.** The series are scrapeable; nothing renders them.
3. **The API role scrapes the DB.** Four queries per scrape on the same pool as requests. At a
   15-second scrape interval that is negligible; a pathological scraper is limited by the pool's
   acquire timeout, not by anything here.
