# T-090 — Contract: bersihkan jaring rolling deploy versi produk

Status: **implemented, menunggu test DB + CI + deploy** (branch `feat/fase2`). Bergantung D-119/D-120.

## Lingkup

T-086 sudah ter-deploy (produksi berjalan beberapa rilis). Setelah dipastikan **tidak ada binary
lama** (cek versi proses / `/healthz`), jaring rolling deploy yang dipasang `product/0003` dilepas
lewat migrasi contract **baru** — `0003` tidak diedit (checksum `platform.schema_migration` dijaga).

## Perubahan

- **`modules/product/migrations/0006_product_version_contract.sql`** (baru). Header
  `-- dbtools:contract` + `-- dbtools:destructive` (DROP TRIGGER/FUNCTION + DROP DEFAULT):
  - `DROP TRIGGER product_version_fill_maker` + `DROP FUNCTION product.fill_version_maker()`
    (trigger yang mengisi `maker = coalesce(maker, published_by)`).
  - `ALTER TABLE product.product_version ALTER COLUMN status DROP DEFAULT` (DEFAULT `'DRAFT'`).
  - **Invarian dipertahankan:** trigger `product_version_guard_insert` +
    `product.guard_version_insert()` ditambahkan — isi penjagaan "versi baru harus DRAFT, belum
    sealed, tanpa keputusan awal, dan `maker = published_by`" dipindah ke trigger baru **tanpa**
    mengisi kolom. Alasan: temuan MAJOR review T-086 r1 (INSERT langsung bisa membuat
    `ACTIVE`/`REJECTED` tanpa binding) tetap perlu tertutup, dan test DB-nya
    (`itproduct` "INSERT langsung non-DRAFT atau maker palsu ditolak trigger") tidak boleh
    dilemahkan/dihapus. Yang dilepas murni jaring rolling deploy, bukan invarian.
- **`ops/migrations/contract-auto.txt`**: daftarkan `product/0006_product_version_contract` supaya
  deploy boleh menjalankannya otomatis (D-120).
- **`modules/product/tests/itproduct.nim`**: suite `product: contract 0006 (T-090)` — membuktikan
  (a) trigger `product_version_fill_maker` hilang, `product_version_guard_insert` ada, dan DEFAULT
  `status` kosong; (b) `INSERT` tanpa kolom `status` gagal NOT NULL, dan tanpa `maker` gagal NOT NULL
  (gaya binary lama tidak bisa menulis lagi).
- **`modules/product/MODULE.md`**: catatan contract kedua `0006`.

Berkas migrasi lama tidak disentuh. DB kosong: `0006` berjalan setelah expand `0003`, jadi
`fill_version_maker` ada lebih dulu lalu diganti.

## Risiko jendela (binary lama + skema baru)

Contract hanya boleh dijalankan setelah dipastikan tidak ada binary lama. Bila dijalankan terlalu
awal / rollback layanan terjadi setelah contract:

- **Event ganda saat submit:** binary lama menerbitkan `ProductPublished` saat submit (versi
  `DRAFT`); dedup key event (`product.published:<versionId>`) membuat event approve versi yang sama
  diabaikan → konsumen melihat "terbit" untuk versi yang masih DRAFT.
- **Katalog bocor:** instance lama tanpa filter `status` menampilkan DRAFT.
- **Approve/reject 404:** instance lama belum punya rute approve/reject (T-086 baru).
- **Rollback layanan tidak mengembalikan skema:** versi yang dibuat binary lama pasca-contract tetap
  `DRAFT` dan harus di-approve (tidak ada lagi DEFAULT/jaring pengisi). Operator perlu approve manual
  versi yang menggantung.
- **Rollback `--down` tidak dipakai** untuk contract ini: mengembalikan DEFAULT/trigger lama akan
  memasang lagi jaring yang sengaja dilepas. Bila terpaksa, `--down` + keluarkan id dari allowlist
  sebelum push berikutnya (D-120 butir 5).
