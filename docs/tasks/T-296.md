## Scope

`apps/web/tests/e2e/visual.spec.ts` gains one helper and calls it immediately before each of the
two `toHaveScreenshot` calls:

```ts
async function hideBuildVersion(page: Page): Promise<void> {
  await page.addStyleTag({ content: ".kran-footer__version { visibility: hidden; }" });
}
```

Call sites: `:76-84` (login) and `:89-97` (password), inside the `for (const theme of THEMES)` loop,
after the last `expect` and before each `toHaveScreenshot`. The four baselines are then regenerated
once through the existing `workflow_dispatch` path with `update_snapshots=true`, on Linux.

**Why not `dynamicMasks`.** Playwright's `mask` paints an opaque box sized to the element's bounding
box. `.kran-footer__version` is sized by its text, so the box width changes the moment the version
string length changes (`v0.1.21` to `v0.1.100`, or `v0.2.0`), and that changed-size mask is itself a
pixel diff. `visibility: hidden` removes the ink but keeps the space, so the footer geometry is
identical for any version string length and the remaining pixels are stable.

**Out of scope**

- `apps/web/src/**`, `packages/ui/src/**`, `packages/i18n/**`: zero diff. The version stays visible in
  production; this ticket only stops a build artefact from entering a screenshot.
- The `.kran-business-date` mask: it stays, it is a real dynamic value.
- Asserting the version format anywhere: a test that pins `v0.1.21` would rebuild the same trap.
- T-286's 32 px inputs on `/login` and `/app/password`, which these baselines lock: that is a screen
  task, not this one.
- Baseline regeneration for any screen other than the four in `visual.spec.ts`.
