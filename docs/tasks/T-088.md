## 2. Rancangan skema (expand-only, migrasi baru)

Nomor migrasi baru — jangan sentuh berkas lama (checksum):
`modules/deposit/migrations/0001..0004`, `modules/ledger/migrations/0012`,
`modules/platform/migrations/0023..0024`.

**Urutan migrasi ditentukan `(seq, module, filename)`** (`tools/dbtools/lib.nim:migrationsOf`),
dan `deposit` < `ledger` menurut abjad. Konsekuensi keras: migrasi `deposit` dengan seq **≤ 3**
berjalan **sebelum** `ledger/0003` membuat `ledger.journal`. Karena itu tabel yang mem-FK
`ledger.journal` wajib seq **≥ 4** (`deposit/0004_deposit_transaction.sql`), bukan `0003`.

`deposit/0001_deposit_init.sql`
- `CREATE SCHEMA deposit`, `CREATE SEQUENCE deposit.account_seq`.

`deposit/0002_deposit_account.sql`
```sql
deposit.account(
  account_id uuid PK, account_no text NOT NULL UNIQUE CHECK (1..32),
  party_id uuid NOT NULL REFERENCES party.party, product_id uuid NOT NULL REFERENCES product.product,
  product_version_id uuid NOT NULL REFERENCES product.product_version,
  branch_id uuid NOT NULL, account_type text NOT NULL CHECK (= 'SAVINGS'),
  status text NOT NULL DEFAULT 'ACTIVE' CHECK (status IN ('ACTIVE','CLOSED')),
  opened_on date NOT NULL, created_at/by, updated_at/by)
deposit.account_balance(
  account_id uuid PK REFERENCES deposit.account ON DELETE RESTRICT,
  balance numeric(24,4) NOT NULL DEFAULT 0 CHECK (balance >= 0),
  updated_at timestamptz NOT NULL)
```
Index: `account(party_id)`, `account(branch_id)`. Tanpa kolom `currency` (lihat §8).
Tanpa tabel `hold` (belum ada konsumen; D-095 = jangan buat semantik tanpa pemakai). `status`
hanya ACTIVE/CLOSED: DORMANT/FROZEN belum punya aturan → jangan dikarang.

`deposit/0004_deposit_transaction.sql`
```sql
deposit.transaction(
  transaction_id uuid PK, tx_type text CHECK IN ('CASH_DEPOSIT','CASH_WITHDRAWAL','TRANSFER'),
  account_id uuid NOT NULL REFERENCES deposit.account,
  counter_account_id uuid REFERENCES deposit.account,
  amount numeric(24,4) NOT NULL CHECK (amount > 0),
  business_date date NOT NULL, journal_id uuid NOT NULL UNIQUE REFERENCES ledger.journal,
  narration text, created_at, created_by,
  CHECK ((tx_type='TRANSFER') = (counter_account_id IS NOT NULL)),
  CHECK (counter_account_id IS NULL OR counter_account_id <> account_id))
```
Index `(account_id, business_date DESC)`.

**Cara saldo dijaga — dipilih: cache satu baris + UPDATE bersyarat**
`UPDATE deposit.account_balance SET balance = balance + ? WHERE account_id = ? AND balance + ? >= ?`
(untuk tarik/PB sumber: `AND balance - ? >= min_balance`). 0 baris = 409 saldo kurang; `CHECK
(balance >= 0)` tetap backstop DB kalau jalur lain menulis. Baris terkunci otomatis → dua koneksi
bersamaan terserialisasi.
Trade-off:
- vs `SELECT ... FOR UPDATE` + cek di aplikasi: dua statement, hasil sama, kalah roundtrip.
- vs jumlahkan `ledger.journal_line` tiap transaksi: benar secara teori tetapi **tidak bisa dikunci**
  (dua penarikan bersamaan sama-sama lolos) dan O(n). Ledger tetap sumber kebenaran (spec §9.1(4));
  rekonsiliasi cache↔ledger = task day-close Fase 3 (dicatat ACCEPTED-LIMITS).

## 3. Pemetaan ke ledger

COA yang ada (`ledger/0002`): `101` KAS, `201` SIMPANAN ANGGOTA, `202` SIMPANAN BERJANGKA.
Rule yang sudah ada (`ledger/0005`): `DepositPosted` = D 101 / K 201.

`ledger/0012_ledger_posting_rule_deposit.sql` (idempoten, `ON CONFLICT DO NOTHING`):
| Event (`journal.source_event`) | Debit | Kredit | Dipakai |
|---|---|---|---|
| `DepositPosted` (sudah ada) | 101 KAS | 201 SIMPANAN | setor tunai |
| `DepositWithdrawn` (baru) | 201 | 101 | tarik tunai |
| `DepositTransferred` (baru) | 201 | 201 | PB antar rekening |

Semua akun datang dari `ledger.posting_rule_line` (data), bukan literal di kode — §10.5 "COA &
posting rule" sebagai parameter. Pembatasan T-088 ke `product_type = SAVINGS` supaya `201` benar;
`202` menunggu task deposito.

Posting sinkron: fungsi composition root baru `apps/api/src/deposit_posting.nim` memakai
`ledger/domain/posting.selectRule` + `buildLines` + `ledger/infrastructure/journal_repo`
(pola `handlers_journals.handleReverseJournal`), **bukan** worker outbox.
Penjaga wajib: event outbox yang diterbitkan **tidak boleh** ber-header `"accounting": true`,
kalau tidak `apps/api/src/posting.nim:isAccounting` akan memposting jurnal kedua. Yang diterbitkan:
`CashTransactionPosted` (payload transaksi) + `journal.posted`, keduanya non-akuntansi.
`journal.idempotency_key = "teller:" & principalId & ":" & key` (≤200 char) sebagai lapis kedua.

## 4. API

| Endpoint | Izin | Sukses | Error |
|---|---|---|---|
| `POST /api/v1/deposit/accounts` | `deposit.account.manage` | 201 `{accountId, accountNo, balance:"0.0000", status, productCode, branchId, openedOn}` | 400 body/amount; 403; 409 `product_not_active`/`party_not_active`/`branch_mismatch`; 409 idempotensi |
| `GET /api/v1/deposit/accounts/{accountId}` | `deposit.account.read` | 200 akun + `balance` | 403 (gerbang cabang), 404 |
| `GET /api/v1/deposit/accounts?partyId=` | `deposit.account.read` | 200 `{items:[]}` | 400 uuid, 403 |
| `POST /api/v1/teller/cash-transactions` | `teller.transaction.post` | 201 `{transactionId, journalId, accountId, direction, amount, balanceAfter, businessDate}` | 400 arah/amount/narration; 403; 404 akun; 409 `insufficient_funds`; 409 `period_closed`; 409 `account_not_active`; 409 idempotensi |
| `POST /api/v1/teller/transfers` | `teller.transaction.post` | 201 `{transactionId, journalId, sourceAccountId, destinationAccountId, amount, sourceBalanceAfter, businessDate}` | 400 akun sama/amount; 409 `insufficient_funds`/`period_closed`; 409 idempotensi |

- Nominal = string desimal (`Money.toDecimalString`), bukan number JSON (D-097, tanpa float).
- `Idempotency-Key` wajib di ketiga POST (pola T-085: `requireIdempotencyKey` → 400; replay 200 +
  `Idempotent-Replayed: true`; hash beda 409; in-flight 409 + `Retry-After` ≤ 60 s, D-117).
- Repo tidak memakai 422 (katalog `problem.nim` hanya punya 400/409/...) → validasi = **400**.
- Semua POST `withDbTx` + `withIdempotency` di dalamnya (klaim, mutasi saldo, jurnal, outbox satu tx).
- `businessDate` dari `businessDateFor(db, institutionScope(), ...)`, bukan jam server.
- Gerbang cabang: `authorizedAtBranch(db, principal, branchId, perm)` setelah cabang akun diketahui.
- OpenAPI: 5 operasi baru + header/409/`Idempotent-Replayed`; `./task openapi-gen` untuk
  `packages/api-client/src/generated/schema.d.ts`; `tcontract` membandingkan `routes.nim` ↔ kontrak.

## 5. Uji

Unit/property (`modules/deposit/tests/t*.nim`):
- saldo: mutasi tidak pernah negatif; tarik tepat sebesar saldo → 0 (boleh), lebih → ditolak;
  `min_balance` dari binding versi produk (bukan konstanta).
- double-entry: `buildLines` untuk 3 event menghasilkan 1 debit + 1 kredit, total seimbang.
- idempotensi: `canonicalOf`/hash stabil; kunci > 200 char ditolak.

Integrasi (`modules/deposit/tests/it*.nim`, `apps/api/tests/itapi_teller.nim`):
- dua koneksi bersamaan menarik saldo 100 (2×60): satu sukses, satu 409, saldo akhir 40 — bukan -20
  (pola `itledger`/`itjournal`, `lock_timeout` + cek `pg_blocking_pids`).
- PB bersamaan dua arah (A→B dan B→A): tidak deadlock (urutan kunci deterministik), saldo akhir benar.
- vs tutup periode (pola T-080 `itjournal`): periode ditutup di sesi lain → POST 409 `period_closed`
  dan **saldo tidak berubah** + tidak ada `deposit.transaction` (bukti satu transaksi DB).
- replay kunci sama → 200 + `Idempotent-Replayed`, tepat satu jurnal; kunci sama body beda → 409.
- tepat satu `ledger.journal` per transaksi (regresi anti double-post outbox).
- DB langsung: `UPDATE deposit.account_balance SET balance = -1` ditolak CHECK.
- mutation check wajib: hapus `AND balance + ? >= 0` **atau** CHECK saldo → test harus FAILED.

a11y/e2e (hanya T-088d): axe 2 tema, keyboard-only (input nominal → konfirmasi → sukses),
`formatMoney` 2 desimal untuk tunai (D-097).

## 9. Risiko + urutan eksekusi

| Risiko | Mitigasi |
|---|---|
| Jurnal ganda (sinkron + worker outbox) | Event outbox tanpa header `accounting`; test "tepat satu `ledger.journal` per transaksi" |
| Urutan migrasi: `deposit` < `ledger` pada seq sama | Tabel ber-FK `ledger.journal` ditaruh di `deposit/0004` (bukan 0003) dan diverifikasi di DB uji kosong |
| Deadlock PB dua arah | Kunci dua baris saldo dengan urutan `account_id` yang deterministik |
| Saldo berubah walau jurnal gagal | Satu `withDbTx`; test 409 `period_closed` memastikan saldo & baris transaksi tidak ada |
| `db` deadline 20 s per blok (D-065) | Transaksi teller = 3–5 statement; tanpa pembacaan besar |
| `response_body` idempotensi menyimpan saldo/nomor rekening | Penerimaan pilot D-118; O-093 tetap terbuka (jangan ditutup oleh T-088) |
| Cache saldo menyimpang dari ledger | Rekonsiliasi = task day-close Fase 3; catat di ACCEPTED-LIMITS |
| Nomor rekening bentrok (sequence vs unique) | `account_no UNIQUE` + retry? **Tidak** — sequence tidak mundur; bentrok = bug, gagal terlihat |

Urutan (gelombang):
1. **Gelombang 0 (serial, gate)**: T-088a. Tidak ada yang bisa paralel sebelumnya.
2. **Gelombang 1**: T-088b (backend transaksi). T-088d **tidak** bisa mulai (butuh API).
3. **Gelombang 2 (paralel aman, file disjoint)**: T-088c (backend PB) ∥ T-088d (UI setor/tarik).
   File bersama: `routes.nim`, `handlers_teller.nim` → c milik backend; d hanya web/i18n.
4. **Gelombang 3**: T-088d tab PB, lalu T-095.

Test DB **tidak boleh bersamaan**: satu DB dev dipakai `task ci` yang sedang berjalan; semua
`it*`/`e2e` dijalankan serial (`./task verify <suite>`), tidak paralel antar-agen.
