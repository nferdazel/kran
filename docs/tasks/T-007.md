# T-007 — Kalender kerja + business date

Spec: §9.3 (DDL business date), §11.2 (konsep business date & level penutupan),
§10 (nilai bisnis dari parameter), §10.4 (mutation test param).

## Scope

Menyediakan dasar kalender untuk day-close (Fase 3) tanpa membangun framework-nya:

1. **Domain murni** `modules/platform/domain/calendar.nim`: bentuk kalender (`CalendarShape`),
   hari kerja/libur, hari kerja berikutnya/sebelumnya, hari kerja terakhir bulan, penentuan
   level penutupan (kaskade `EOD` → `+EOM` → `+EOQ` → `+EOY`), state business date + tabel
   transisi sah.
2. **Skema** `modules/platform/migrations/0005_platform_calendar.sql`: `platform.holiday`
   (termasuk `recurring_annual`) dan `platform.business_date`.
3. **Repository** `modules/platform/infrastructure/calendar_repo.nim`: baca bentuk kalender
   dari parameter + tabel libur, lifecycle business date (`ensure`, `transition`, `rollover`),
   `workingDayInfo`.
4. **Parameter baru**: `platform.calendar.weekend_days` (json array nomor hari ISO), disemai
   pack `base` sebagai `[6,7]`.
5. **Test**: `tests/tcalendar.nim` (murni) dan `tests/itcalendar.nim` (integrasi DB).

Di luar scope (sengaja): orkestrasi day-close (`daycloser`, Fase 3), `EOW` (opsional §11.2,
butuh parameter hari penutupan mingguan), reopen/reverse EOD (§11.7 butuh kebijakan approval
berjenjang), API/OpenAPI (T-008) dan UI (T-010).

## Keputusan & catatan desain

- **Nilai kalender tidak ada di kode**: akhir pekan & awal tahun fiskal dari parameter, hari
  libur dari tabel. Tidak ada fallback: parameter tanpa nilai aktif → error (§10.6).
- **`CloseLevel` untuk sementara tinggal di domain kalender** karena kalender yang memilih
  levelnya. Saat modul `daycloser` lahir (Fase 3) tipe ini pindah ke sana dan modul ini hanya
  menyediakan `closeLevelsFor`. Dicatat di MODULE.md supaya perpindahan itu tidak mengagetkan.
- **Hari bukan hari kerja → tidak ada penutupan** (`closeLevelsFor` mengembalikan himpunan
  kosong). Ini sinyal bagi orkestrator bahwa tanggal itu tidak perlu ditutup.
- **Transisi state dijaga dua lapis**: `canTransition` (raise `ValueError` untuk jalur ilegal,
  termasuk `OPEN → CLOSED` dan reopen) dan `UPDATE ... WHERE state = expected` (return `false`
  bila state di DB sudah bergeser) — pola compare-and-set.
- **Rollover tidak memvalidasi tanggal**: pemanggil memakai `nextWorkingDay` dari kalender.
  Repo tidak boleh menebak kebijakan hari kerja; ia menyimpan keputusan pemanggil.
- **Hari libur berulang** disimpan sekali dengan bulan/tanggal acuan dan diperluas per tahun
  saat dibaca; 29 Februari pada tahun non-kabisat dilewati (tanggalnya tidak ada).
- **`holidayDates` menyaring non-recurring ke rentang tahun yang diminta** — supaya bentuk
  kalender `asOf`-tahun±1 tidak membawa libur tahun jauh yang tidak relevan.
- **Deviasi DDL spec §9.3** (lihat DECISIONS D-011): kolom `current_date` diganti
  `current_business_date` (kata kunci SQL, syntax error bila tanpa kutip) dan keunikan scope
  dijaga `UNIQUE INDEX (scope_type, COALESCE(scope_id,''))` karena ekspresi tidak boleh dipakai
  di `PRIMARY KEY` Postgres. `scope_id` bertipe `text` supaya seragam dengan `param_value`.

## Kriteria selesai (dari backlog)

| Kriteria | Bukti |
|---|---|
| Hari libur dari param/tabel | `itcalendar`: `addHoliday` + `workingDayInfo`, libur berulang diperluas, libur cabang tidak bocor ke institusi |
| Level close terpilih dari kalender | `tcalendar` + `itcalendar`: {EOD}, {EOD,EOM}, {EOD,EOM,EOQ}, {EOD,EOM,EOQ,EOY}; akhir tahun fiskal April → EOY di akhir Maret; akhir tahun fiskal Februari → EOY tanpa EOQ |
| Transisi state ditolak bila ilegal | `tcalendar`: tabel transisi; `itcalendar`: raise untuk `OPEN→CLOSED`/reopen, `false` untuk CAS yang kalah, rollover hanya dari `CLOSED` |
| (tambahan) param-driven, bukan kode | `itcalendar`: ubah `weekend_days` jadi `[5,6]` lewat maker-checker → hari kerja & hari kerja terakhir bulan bergeser |

## Batasan yang diketahui (jujur)

1. **Override parameter level INSTITUTION tidak terasa dari konteks BRANCH.** `ScopeLookup`
   mengartikan `""` sebagai "tidak diminta", sehingga nilai dengan `scope_id` institusi
   konkret hanya terbaca bila pemanggil menyebutkan id institusi itu. Untuk kalender,
   `weekend_days` disemai di `GLOBAL` (dan bisa ditimpa per `BRANCH`), jadi tidak menghalangi
   T-007 — tapi konvensi lookup ini perlu ditinjau di T-016 (lihat OPEN_ITEMS O-012).
2. **`EOW` belum ada** (opsional di §11.2).
3. **Zona waktu belum dipakai**: bentuk kalender tidak menyimpan timezone; batas hari mengikuti
   jam server. Cut-off time & timezone per cabang (§22) belum bagian dari task ini.
4. **Belum ada UI/API**: belum ada cara manusia mengisi `platform.holiday` selain SQL/ops —
   menyusul bersama T-006/T-010.
