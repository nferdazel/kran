## Scope

1. **Submit.** `effectiveFrom` before the running business date is refused with 400 and reason
   `effective_from_past`. The business date is `businessDateFor(db, institutionScope(), …)` — the same
   value the audit rows and the retirement path use, not a second notion of "today".
2. **Approve.** The same comparison runs again at approval against the business date **then**. A row
   submitted for today and approved tomorrow cannot slip through, and the refusal is 409 because the
   request body carries no date; the conflict is with the row's state.
3. **Failure leaves the row intact.** A refused approval does not burn the submission: once the
   business date is back within range the same approval succeeds (asserted in the test).

Deliberately not changed: the audit `businessDate = effectiveFrom` convention itself (it is what makes
history readable), the retirement path (already guarded), and the default `effectiveFrom` when the
field is omitted (today, which passes the new guard).

## Acceptance

Submitting a value dated before the running business date returns 400 `effective_from_past` and writes
nothing; approving a pending value whose date has since passed returns 409 `effective_from_past` and
leaves it `PENDING`.

## Notes

- The comparison is a string compare on ISO `yyyy-MM-dd`, which is chronological for that format and
  is applied only after `isIsoDate` has accepted both sides.
- 409 (not 400) at approval is deliberate: the client sends no date there, so the refusal is about the
  row's state, matching `not_pending` / `period_conflict` / `effective_to_without_successor`.
- Open item, not fixed here: a value can still be submitted for today and approved late in the day
  after a rollover; the guard closes it at approval, but the UI does not warn before submitting.
