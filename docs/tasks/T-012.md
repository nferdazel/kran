## Keputusan desain

- **Tidak ada use case application-layer baru untuk submit/approve.** Handler memanggil
  `param_repo.submitChange/approveChange` di dalam `withDbTx` persis seperti pola test integrasi;
  memindahkannya ke `application/` tanpa port (`ParamSource`-style) menambah lapisan tanpa
  konsumen kedua. Bila nanti ada CLI/batch yang memakainya, pemindahan itu jadi refactor kecil.
- **Uniformitas daftar parameter**: satu rute `GET /api/v1/params?status=` melayani daftar aktif
  dan daftar persetujuan (yang kedua = filter `status=PENDING`), bukan dua rute berbeda.
- **Sesi jadi pemilik otorisasi realtime** (melunasi D-021 "deny-all sampai T-012"): `canOpen`
  memvalidasi cookie sesi, `allowedTopics` memetakan topik → izin (`param.changed` →
  `platform.param.read`). **Tanpa wildcard implisit**: `*` selalu ditolak dan klien wajib
  menyebut topiknya — aturan yang sama dengan `splitAllowed` di hub (D-024).
- **Origin tunggal via proxy dev**: Vite (`preview.proxy`/`server.proxy`) meneruskan `/api` ke
  `cbs-api`, sehingga cookie `SameSite=Strict` tetap berlaku tanpa CORS+`credentials`. Ini juga
  bentuk produksi (satu origin di belakang Caddy).
- **Seed user hanya untuk dev/e2e** dan bertanda jelas; bootstrap user produksi (siapa admin pertama,
  password awal, wajib ganti) **belum diputuskan** → item terbuka, bukan ditebak di sini.
